# 并行派活落地设计

> 状态：草案，待产品负责人审阅。审过之前不改内核。
> 日期：2026-11-09
> 范围：team-kit 内核（`template/`、`profile/` 模板、`bin/kit`）。两个工程（vista、prism）的配置怎么改，只记成它们自己的工作项，本设计不替它们改。

## 1. 为什么要做

产品负责人的诉求（2026-11-08 原话整理）：

1. **全链路**：做迭代规划时就要考虑迭代之间的依赖和先后，判断哪些迭代可以并行开发。
2. **增量链路**：要判断多个开发任务、多个测试任务能不能并行。
3. 判断能并行，就要**尽量按并行的方式派活**。

现在的契约里有「同角色并行」一节，但实际很少用到，原因有四：

- **契约默认串行。** §三「同角色并行」只说「SA 决定」，并且列了四个前置条件，「有一条不满足就串行」。
- **全链路写死了逐轮执行。** §二.4 阶段 3 是「按迭代规划，逐轮执行」。prism v2.1.0 想并行时，只能由负责人逐版特批：D29 授权最多两条开发线，D45 改为三条，计划里还专门写了「契约 §二.4 规定逐轮执行」。
- **增量链路没有讲多个工作项同时进行。**
- **前置条件和实际做法冲突。** 前置条件要求「都在同一工作树内」，但实际做法是各线把代码导出到 `/tmp` 各自构建、各自测试，用来隔离。同一工作树里的多条线还共用一个 git 暂存区。prism v2.1.0 出过实际事故：I1 线的删除改动被 I2 线的提交 `6e9d7e5` 一起带走。之后才有「并行线共用暂存区」这个契约缺口和 v0.6.0 的带路径提交规则。

## 2. 目标、不做、反目标

**目标**

- **规划时就判断能否并行。** 并行与否在规划阶段判定并写下来：全链路写进迭代规划，增量链路在同时开工两项以上时写一段简版。
- **默认并行。** 能并行就并行；选择串行要在账本里写理由。
- **写代码的并行线互不干扰。** 每条线有自己的工作树和分支，暂存区、构建产物、测试环境都分开。
- **单台测试服务器也能支撑各迭代各自验收。**
- **合入、迁移编号、共享文件这几处交汇点有明确规则。** 写清谁来做、按什么顺序、出了冲突怎么办。

**不做**

- 不改验收的权属：迭代验收、版本验收、合入 `main` 仍由产品负责人一句话决定。线合入 `develop` 是 SA 的集成动作（D3、§5.6.1）。
- 不改评审规则：建议级、一轮。
- 不做自动调度工具。派活仍由 SA 按契约人工判断，账本只记录状态。
- 不替工程改它们的部署脚本，也不替它们实现多个测试服槽位。

**反目标**（技术上做到了，但出现下面任一情况就算失败）

- 并行之后 SA 花在合并、解冲突、搬运文件上的时间，比省下来的时间还多。
- 为了并行而拆出本来不需要的工作项，导致账本里的行数和评审次数翻倍。
- 某条线的问题拖住所有线，或者一条线未经验收的改动被当成「已验收」混进 `main`。
- 账本、评审证据里引用的 `commit:path` 因为改写历史而失效。

## 3. 约束

- **内核文件在所有工程里逐字相同。** 工程特有的取值（工作树放在哪、最多开几条线、测试环境怎么隔离）只能放进 `profile/` 生成的 `docs/rules/工程配置.md`。
- **`工程配置.md` 只在缺失时生成。** 已安装的工程不会自动拿到新增的节，需要各工程自己补。
- **账本已经支持多工作树。** `team-ledger.py` 按 `git rev-parse --git-common-dir` 定位主工作树，在任何工作树里落账都写进同一本账（`team-ledger.py:80`）。
- **钩子已经支持多工作树。** `core.hooksPath=.githooks` 是相对路径，存在共享的 `.git/config` 里，每个工作树用的是自己检出的 `.githooks/`。
- **git 的实际行为**（git 2.50.1 实测）：
  - 主工作树里如果有别人**已暂存未提交**的内容，`git merge` 会整体拒绝，报 `would be overwritten by merge`，而且不留任何中间状态。
  - 只有**未暂存**的改动时，只要合并不涉及这些文件，`git merge` 能成功。
  - 冲突合并的中间状态里，`git commit -- <路径>` 会失败（不允许部分提交）。所以主工作树绝不能停在冲突状态。
  - 用底层命令（`merge-tree` 加 `commit-tree` 加 `update-ref`）绕过检查合并，会让主工作树的文件和暂存区跟分支脱节，不可取。
- **Flyway 不接受乱序版本号。** 测试服已经执行过 V6 之后，再部署 V5 会被拒绝。另外，已执行的迁移脚本不得修改。
- **prism 本机没有 Docker。** 它的镜像在服务器上构建，所以各线的隔离测试环境可能要放在测试服上，用不同的 compose 项目名、库名和端口区分。prism v2.1.0 已经这样做过（`prism-verify-<轮次>`）。

## 5. 设计

### 5.1 什么时候判断能否并行，判断结果写在哪

| 场景 | 什么时候判 | 写在哪 |
|---|---|---|
| 全链路 | 阶段 2「系统设计与迭代规划」 | 迭代规划里新增一节，名为「并行编排」（必填，§5.2） |
| 增量链路 | 同一时间段里有两个以上增量工作项要开工时（快速链路工作项不开线，见 §9 C10），SA 判级之后、派活之前 | 新增工作项 `并行编排-<日期>`：一段账本 note，必要时另写一页文档（简版，§5.2 末尾） |
| 迭代或工作项内部 | 一份 spec+plan 里的 task 可以拆给多个 SE，或测试用例可以拆给多个 QA | 现有「同角色并行」规则不变，只是放宽了前置条件（§5.7） |

**默认并行。** 只要依赖关系允许，就按并行编排。选择串行要写一条账本 note，说明哪一项依赖或哪一项资源不允许并行。没有写理由就串行，SA 每回合巡检时会把它查出来（§5.8）。

**能否并行的判据：**
- 两份工作之间，有没有一方需要另一方**还没冻结**的接口或数据结构；
- 有没有改同一批文件、同一张表；
- 资源（测试环境、机器负载）能否隔离。

依赖只体现在接口上的，接口冻结之后就可以并行，不必等上游验收。

### 5.2 「并行编排」一节写什么

全链路的迭代规划必须写这一节，内容如下。

1. **依赖图**：每个迭代依赖谁，依赖的是什么（接口、表、数据、判据）。
2. **线的划分**：
   - 每条并行线承载哪个或哪几个迭代；
   - 线的短名（ASCII，用作分支名和目录名）；
   - 什么时候开工，开工条件是「某接口已在某提交冻结」或「某线已合入」。
3. **接口冻结点**：下游线开工前，上游必须先提交并冻结的接口（类型、接口契约、表结构）。冻结点以提交号为准。冻结之后要改，必须报 SA，由 SA 通知所有受影响的线。
4. **归属**：
   - 每条线能改哪些路径；
   - 共享文件（公共框架包、`.gitignore`、根配置、依赖清单）归谁改，其他线需要改时报 SA；
   - 每条线有几个迁移脚本（只写数量，不写编号，见 §5.5）。
5. **合入顺序**：预定的合入顺序，也就是测试服的验收顺序。合入顺序可以按实际进度调整，调整时落账说明。
6. **并行线数**：同时活跃的写代码线不超过「最多并行线数」：内核默认 3，工程配置可另设（D6）。

**增量链路的简版**只写四项：哪几项并行、各自能改哪些路径、共享文件归谁、合入顺序。多数情况一段账本 note 就够了。

### 5.3 并行线（写代码的线）

**一条并行线 = 一个工作树 + 一个分支**，承载一个迭代或一个增量工作项的全部代码类产出。

**创建（SA 做，在派出第一棒之前）：**
- 分支名：`lane/<短名>`，从开工条件对应的提交上拉出。
- 工作树放在工程配置里指定的位置。默认是工程根目录**之外**的同级目录 `../<工程目录名>.lanes/<短名>`。放在工程内部的话，工程里的测试、lint、grep、钩子扫描可能会扫进嵌套的工作树。
- 新工作树里没有被 git 忽略的本地文件，比如依赖目录、本地凭据、`.env`。按工程配置里的「工作树初始化」命令准备好；没有命令就写「无」。
- 落账：在该工作项的 note 里写明短名、分支、工作树路径、起点提交。

**什么提交在线分支上，什么提交在 `develop` 上：**

| 产出 | 提交到 |
|---|---|
| 该线的 spec+plan、代码、研发自测试、QA 的测试方案+用例、可执行用例、测试报告、QA 证据 | 线分支（在线的工作树里提交） |
| 版本级文档（需求文档、UI 原型、系统设计与迭代规划、PM 结论只落账）、不属于任何线的文档类工作 | `develop`（在主工作树里带路径提交，规则不变） |

评审和取证照旧用 `commit:path` 指认。各工作树共用同一个对象库，线分支上的提交随时可读。

**谁在线的工作树里干活：** 该线的 SE（可以有多个，属于线内的同角色并行），以及给该线做测试的 QA。PM 做界面审查、SA 做评审时只读，不需要进这棵工作树，按提交读即可。

**线内流程不变**：仍是 spec+plan → SA 评一次 → 扇出 QA → 编码与研发自测 → QA 独立测试 → 测试报告。

**不改写历史：** 线分支上不做 `rebase`、`squash`，也不 `push --force`。原因是账本和评审里引用的 `commit:path` 必须一直可读。需要上游的改动时，用 `git merge develop` 合进线分支。

**收尾：** 线合入 `develop` 之后：
- 先确认工作树里没有未提交的产出：证据要么已经提交，要么已按 QA 规则另存；
- 再执行 `git worktree remove` 和 `git branch -d lane/<短名>`；
- 删除前先看目标里有什么，遵守 AGENTS「覆盖类操作先读目标」。

### 5.4 线内的测试环境

- QA 的系统测试在**该线自己的隔离环境**里跑，不占用测试服的验收部署。
- 隔离环境的具体做法由工程配置写明，包括端口、数据库、compose 项目名、临时目录、浏览器 profile。可以在本机，也可以在测试服上用不同前缀并排部署（prism 的做法）。现有「并行测试的隔离参数」一行合并进新的「并行线」一节（§6）。
- QA 的测试报告必须写明被测提交，也就是线分支上的提交号。

### 5.5 合入 `develop`

由 SA 合入，按并行编排定的顺序。前提是该线的 QA 测试报告已经提交。

**报告里有 `阻断` 时：** 先在线内修复，修好后重测受影响的部分，再合入。这一条是我的判断（§9 C3）。它和 §五「`阻断` 不自动拦合入」并不矛盾：§五说的是合入 `main` 的权力归负责人；这里是把有阻断问题的线挡在 `develop` 外面，免得拖累其他线。负责人的裁定权不受影响。

**合入步骤：**

1. **先预检冲突，不动工作树。** 运行 `git merge-tree --write-tree develop lane/<短名>`。
   - 有冲突：退回该线，由线的 SE 在线的工作树里 `git merge develop`，解决冲突，跑研发自测，提交后重新报 SA。**SA 不在主工作树里解决冲突。**
2. **迁移编号。** 该线的迁移脚本在线内使用占位编号。合入前由线的 SE 改成 `develop` 上的下一个空号，在线分支上提交。
   - 线内的隔离库是一次性的，改名不影响「已执行脚本不得修改」。
   - 合入以后，编号再也不能改。
3. **在主工作树里合入。** 执行 `git merge --no-ff lane/<短名>`。
   - 主工作树的暂存区里有别人已暂存、未提交的内容时，git 会拒绝合并，主工作树保持原样。此时 SA 稍后重试，**不替别人取消暂存**。
   - 文档线的暂存只在「add 之后马上带路径提交」的一瞬间存在，所以等待通常很短。
4. **合入后的集成自测。** 合并提交上从来没有人整体跑过测试。由刚合入那条线的 SE 在这个合并提交上跑「构建 + 研发自测全量」，全绿之后才能部署验收。做法：线的工作树 `checkout --detach <合并提交>`，或者另开一个临时工作树。失败就在 `develop` 上修，见 §5.6。这一条是我的判断（§9 C4）。
5. **落账：** 合并提交号、合入了哪条线、迁移编号、集成自测结论。

### 5.6 测试服与验收

- 测试服上**同一时间只放一个部署**（槽位数为 1 时）。部署对象一律是 `develop` 上的某个提交，不部署线分支。
- **排队顺序 = 合入顺序。** 一条线合入并且集成自测通过之后，SA 部署当时的 `develop` 头，通知负责人验收。
  - 如果前一个验收还没结束，新的部署要不要立刻覆盖，由 SA 判断：覆盖后，正在验收的那个迭代的改动仍然包含在新部署里，因为部署是累加的。正在进行的验收换一个提交接着做，结论注明是基于哪个提交。
  - 负责人正在操作的时候不覆盖。
- **一次部署可以出多份结论。** 每个迭代的验收结论单独落账（PM 的需求符合性 note ＋ 负责人一句话），各自注明基于哪个部署提交。迭代 B 的验收里带着迭代 A 的改动，这是允许的（D4）。
- **验收不通过：**
  - 在 `develop` 上修，不回退。修复由原线的 SE 做，开一条短修复线 `lane/<短名>-fix<N>`，走 §5.5 合入。
  - 修复线可以只跑受影响的测试，QA 是否复测由 SA 按改动范围决定。
  - 修好后重新部署，受影响的验收项重做。
- **测试服的占用记录在账本里**，用一个专门的工作项（如 `测试服验收`）：
  - 部署时落 `进行中`，note 写「部署 `<提交>`，包含 `<线…>`，供 `<迭代…>` 验收」；
  - 等负责人验收时落 `阻塞 --blocker-role owner`，这样会进入待裁决清单；
  - 没有待验收的内容时落 `完成`。
  - 任何时候都能从账本读出测试服上现在是哪个提交、在等谁。
- **槽位数大于 1 的工程**，按工程配置把各槽位分给不同的线，账本里的工作项按槽位分开。部署脚本怎么支持多槽位是工程自己的事。

### 5.6.1 进 `main`（D5）

- 线合入 `develop` 是 SA 的集成动作，不需要负责人那一句话。负责人的「合入一句话」管的仍是 `develop` 合入 `main`（按工程配置「分支与发布」）。
- **`develop` 整体进 `main` 的前提**：从上一次进 `main` 以来，合入 `develop` 的每一条线和每一个快速项都已经有验收通过的结论。有任何一项未验收、或者验收不通过还在修，就先不进。
- SA 在请负责人一句话时，列出这次会带进 `main` 的各项及各自的验收结论。
- 想让先通过的项尽早进 `main`，办法是在并行编排里把它排在前面、让后面的线晚些合入 `develop`，而不是从 `develop` 里单独挑出来（单独挑会改写历史，和 C2 冲突）。
- 全链路不受影响：版本内各迭代本来就在系统验收之后才进 `main`。

### 5.7 「同角色并行」规则的修订

现有的四个前置条件改为：
- 各份工作互不依赖，或者依赖的接口已冻结；
- 改动路径不重叠；
- 资源各自隔离；
- **写代码的线各用自己的工作树和分支**（§5.3）。

只写文档的实例仍可留在主工作树，带路径提交。「有一条不满足就串行」改为「不满足的部分串行，其余仍然并行」。

### 5.8 SA 的职责变化

- **有线在跑的时候，SA 不写产品代码。** SA 只做派活、评审、合入、部署和落账，把精力留给交汇点。
  - 合入冲突退回线内（§5.5），集成自测和验收修复交给线的 SE。
  - 基建工作（AGENTS 里的「两顶帽子」）不受这条限制。
- **每回合巡检从两步改为三步。** 新增第 3 步：对照并行编排，找出「已满足开工条件、却还没有派出」的线，以及「已有 QA 报告、却还没有合入」的线；没有写串行理由的也在这一步查出。
  - 落地方式（§9 C6）：
    - 这一步写进 `team-ledger` SKILL 的「SA 值守的每回合三步」，`双端协作与交接.md` 的「账本巡检」一行同步改名；
    - 先靠 SA 读并行编排人工对照，不新增脚本命令。
- **最多并行线数**：内核默认 3，工程配置可另设。SA 开线时不得超过。

## 7. 对工程的影响（只记录，不替工程改）

- **两个工程的「分支策略」都明确写了不另建分支或工作树：**
  - vista：「不另建特性分支或 worktree」；
  - prism：「不再按特性、BUG 或角色另建分支 / 工作树」。
  
  同步新内核之后，它们的工程配置和内核会冲突，需要各自的 SA 改分支策略：允许 `lane/*` 分支和并行线工作树，并且补上「并行线」一节。kit 发版时，在两个工程的账本里各挂一个工作项（`parallel-lanes-adopt`，接续方 SA）。
- **兜底**：契约写明，工程配置还没有「并行线」一节时，**不开并行线**，按原规则执行（同一工作树、带路径提交、默认串行）。这样工程同步内核后、改分支策略之前，规则不打架（§9 C9）。
- 两个工程目前都有进行中的版本：prism 在 v2.1.1，按 §10.0 自行并行。新规则只用于**新开的迭代或工作项**，进行中的不追溯。
- vista 主工作树之外还有 Codex 自建的工作树（`~/.codex/worktrees/…`），和本设计的线工作树互不相干。巡检时按账本里登记的线来认，不按 `git worktree list` 的全部条目来认。

## 9. 我（维护方）做的判断，请审阅时重点看

| # | 判断 | 理由 |
|---|---|---|
| C1 | 工作树默认放在工程外的同级目录 `../<工程目录名>.lanes/<短名>` | 放在工程内部会被测试、lint、grep、钩子扫描扫进去 |
| C2 | 线分支不 rebase、不 squash，上游改动用 merge 合进来 | 账本和评审里的 `commit:path` 必须一直可读 |
| C3 | QA 报告有 `阻断` 时，先在线内修好再合入 `develop` | 把问题挡在 `develop` 外面，不拖累其他线；合入 `main` 的裁定权仍归负责人 |
| C4 | 合入后由线的 SE 在合并提交上跑「构建 + 研发自测全量」，通过后才部署 | 每条线单独测过，不代表合在一起没问题；在合并提交上测比在验收时才发现便宜。代价是每次合入多跑一轮自测（prism 的全量 Java 校验要几十分钟） |
| C5 | 合入冲突退回线内解决，SA 不在主工作树里解冲突 | 主工作树停在冲突状态时，其他人的带路径提交会全部失败（实测） |
| C6 | 巡检第三步先靠 SA 人工对照并行编排，不加脚本命令 | 编排写在文档里，格式还没定型，过早做成脚本就是猜格式 |
| C7 | 新规则只用于新开的迭代或工作项 | 和账本「存量不追溯」一致，不打断 prism v2.1.1 |
| C8 | ~~「最多并行线数」由工程配置，内核不设默认值~~ 已由负责人改为 D6：内核默认 3，工程可另设 | — |
| C9 | 「并行线」是软节：缺失时 `kit check` 只警告，契约兜底为不开线、按原规则执行 | 不替工程改配置，也不让同步后的 check 失败；工程补上这一节就等于选择启用 |
| C10 | 快速链路的工作项默认**不开线**，留在主工作树带路径提交；只有当 SA 判断它和某条线改到同一批路径时，才串在那条线后面或者并进那条线 | 快速项按定义不加页面、不动迁移、不动权限，开线的成本（建工作树、初始化、预检、集成自测）比它本身还大 |
| C11 | 内核里不写死 `develop`，写成「集成分支（工程配置「分支与发布」里的日常开发分支，例如 `develop`）」；本文为了好读仍写 `develop` | 分支模型归工程配置，内核目前也没有规定 `develop` |
