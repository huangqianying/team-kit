# 改动影响分析设计（借鉴 HelixHarness「往后」第 18 条）

> 状态：已批准（2026-11-24）。
> 日期：2026-11-23
> 规模：小改动（简短设计，不做实施者审读）

## 为什么

契约 §二.1 规定复杂度「只看编码规模与影响面」，但影响面现在靠 SA 估。并行线合入前会波及哪些代码、验收修复后要重测多大范围（`并行线.md`「六」：「由 SA 按改动范围定」），目前也都没有方法可依。

HelixHarness 的 `git-diff-impact`（源码 `5bde4b3`，`skills/git-diff-impact/SKILL.md`）是一个按需调用的静态分析方法，可以借来补上这一块。

## 目标、不做、反目标

**目标**：新增内核 skill `skills/diff-impact/`，按需对一段改动做影响分析，在三个环节推荐使用：
1. SA 判复杂度；
2. 合入并行线前；
3. 验收修复后定复测范围。

**不做**：
- 不强制任何环节必须跑（负责人选了方案 A）；
- 不自动修代码、不生成测试；
- 不算评审结论，也不当作测试证据；
- 不加脚本，它是一份方法 skill。

**反目标**：
- 把静态推断写成「已验证」；
- 没覆盖到的调用链被当成「无影响」。

## 方案（负责人选了 A）

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A. 只是工具，三个环节推荐使用（选定）** | 契约和 `并行线.md` 在三处各加一句「可以用 `diff-impact` 判断」 | 不增加流程负担；用不用看 SA |
| B. 合入前、定复测范围前强制跑 | 落账须引用报告 | 每次多一步，而静态分析本身在大改动时覆盖不全 |

## 设计

**`skills/diff-impact/SKILL.md`**：方法照 HelixHarness 的写法，按 team-kit 的口径改写。
- **输入**：
  - 不给引用时，分析未提交改动；
  - 一个引用时，对比该引用与 HEAD；
  - 两个引用时，对比两个提交快照；
  - 「某线引入的改动」以 `git merge-base <集成分支> lane/<短名>` 为基准，并写明实际基准。
- **只读**：
  - 用 `git show <sha>:<path>`、`git grep <模式> <sha> --` 读对应版本，不切换分支，不用工作区代替历史版本；
  - 不读凭据和被忽略的目录。
- **方法**：
  1. 读 `AGENTS.md`、工程配置「项目规范」里的相关规范，以及给定的需求或 spec+plan；
  2. 定位行为变化：接口、类型、配置、数据结构、迁移、默认值、错误行为、副作用；
  3. 至少追踪一层直接调用方，高风险的继续追踪间接调用方，写明路径和行号；
  4. 检查兼容性；
  5. 分级时把「风险等级」和「证据确定性」分开标。
- **兼容性检查**：改写成 team-kit 两个工程用得上的几类：
  - 对外接口与错误码；
  - 配置与环境变量；
  - 数据库迁移，按 Flyway 规则，含已执行脚本不得修改、跨线撞号，并引用 `team-check migrations --refs`；
  - 前端浏览器与断点（引用 `UI设计规范.md` §4.1）；
  - 依赖版本。
  
  不照搬 HelixHarness 的 Objective-C 和 Android 部分。
- **输出**：先在对话里给出主要发现，再给报告。报告包含：
  - 范围：模式、基准和目标提交、排除项；
  - 改动概览；
  - 影响清单：位置、调用方、触发条件、业务影响、风险等级、证据、待验证项；
  - 兼容性；
  - 建议重测的范围；
  - 覆盖边界：没追踪到的调用链、动态调用盲区，并写明「静态分析，未运行测试」。
- **落位**：
  - 默认不存文件，结论写进账本 note（一句话加风险等级）；
  - 用来决定复测范围时，报告存为 `docs/tests/<版本>/影响分析-<工作项>.md` 并提交，账本 note 用 `commit:path` 引用。

**规则文字**：

| 文件 | 改什么 |
|---|---|
| 契约 §二.1 | 「复杂度判据」后加一句：影响面拿不准时，可以用 `skills/diff-impact` 分析 |
| `并行线.md`「五」 | 合入前可以用它看这条线会波及哪些代码 |
| `并行线.md`「六」 | 修复后定复测范围时可以用它，并按上面的规则存报告 |
| `manage-docs` | `docs/tests/<版本>/` 的说明里加上「影响分析」 |
| `AGENTS.md` | 不改：skill 由 `skills/*/SKILL.md` 自动发现 |

**测试**：沿用 kit 现有测试，内核清单和整目录同步会覆盖新 skill。不加专门的代码测试，因为它是方法文档，没有可执行逻辑。发布前请一个子代理按 SKILL.md 对 team-kit 自己的某次提交做一次真实分析，确认这份 skill 能照着执行。

**版本**：v0.11.0。

## 附录 A：发版前试跑（2026-11-24）

**做法**：派一个 sonnet 子代理，只给它 `template/skills/diff-impact/SKILL.md`，按「两个引用」模式分析 team-kit 的 `c0f8eda^..c0f8eda`（v0.10.0 审阅修复，13 个文件，+281/−58），只在对话里输出。原计划用 `4faab13`，那次提交全是新增文件、没有已有调用方可追，测不出「追调用方」这一步，改用改了已有函数的 `c0f8eda`。

**核对结果**：
- 报告六部分齐全，范围写了完整的基准 sha 与目标 sha，覆盖边界写了「静态分析，未运行测试」；
- 风险等级与证据确定性分开标（高 0 / 中 3 / 低 5）；
- 抽查的调用方行号在 `c0f8eda` 上对得上；
- 全程只读：只用了 `git show`、`git grep`、`git diff`、`git ls-tree` 等命令，没有切分支，结束时 `git status` 干净。

**它查出的问题（维护方逐条复现过）**：
- `team-check migrations --refs` 在迁移目录不存在时，输出「无重复」并退出 0；不带 `--refs` 时是「判不了」并退出 2；
- `hook.py` 头注和 `AGENTS.md` 仍写「只提醒、不拦截」，没说子代理结束提醒会让它再走一轮；
- 会话开始注入过滤掉了 stale 里带 `→ OWNER` 的行，而 `owner` 只列 `blocker_role` 为 owner 的项，只用 `--to owner`、没有阻塞的项会两边都不出现。

这些属于 v0.10.0 的内核，不在本设计范围内，记入交接说明 §5.1，修不修由负责人定。

**按试跑反馈改了 SKILL.md 两处**：
- 工程配置里某项还是占位时，相关检查写成待验证项；
- 由外部调用的入口（命令行脚本、钩子、定时任务、部署脚本），把配置文件和文档位置当作调用方列出。
