## 三、设计

### 3.1 内核 ＋ 工程配置

**原则：内核在所有工程逐字相同；工程专属的东西只放三份文件。**

| 位置 | 内容 |
|---|---|
| `template/`（37 个文件，清单 `MANIFEST`） | 内核：`AGENTS.md`、`CLAUDE.md`、`docs/rules/团队协作契约.md`、`docs/rules/双端协作与交接.md`、`docs/rules/UI设计规范.md`（通用规则）与演示页 `docs/rules/ui-demo.html`、`docs/rules/roles/{pm,ui,se,qa}.md`、`.claude/agents/*` 与 `settings.json`、`.codex/agents/*` 与 `config.toml`、9 个 skill（team-ledger、sa-review、technical-review、manage-docs、progress-report、requirements-analysis、insight-discovery、insight-ledger、ui-design）、`.githooks/{pre-commit,install.sh,tests/hooks.test.sh}` |
| `profile/` | 新工程的模板，只在工程里还没有时生成：`docs/rules/工程配置.md`、`docs/rules/UI设计规范-本工程实例.md`、`.githooks/project.conf`；`kit check` 要求三份都在 |
| 工程里的 `docs/rules/工程配置.md` | 产品、目录、命令、分支与发布、部署、项目规范、本工程补充规则。**节名是内核引用的锚点**（内核写「见工程配置「目录」」），`kit check` 会核节名 |
| 工程里的 `.githooks/project.conf` | 钩子的工程参数：`HOOK_CRED_FILE_RE`、`HOOK_TEST_PATH_RE`、`HOOK_CONFIG_PATH_RE`、`HOOK_SECRET_ALLOW_VALUE_RE`、`HOOK_CRED_HINT` |
| 工程里的 `docs/rules/UI设计规范-本工程实例.md` | 本产品的 UI 取值（登录方式、各身份顶栏件数、区域导航、大屏与否、一次性凭据、指标格式、存量断点），按通用规则节号逐节对应 |
| 工程根 `.team-kit.json` | kit 版本号、提交号，以及同步时各内核文件的 sha256 |

不进内核、留在各工程的：部署 skill（`skills/deploy`、`skills/deploy-aitokenreport`）、`e2e-test`、各产品的系统设计规范 / 错误码规范、`qa/` 执行器。

### 3.2 `bin/kit` 命令

| 命令 | 作用 | 保护 |
|---|---|---|
| `install <工程>` | 拷内核、建 `.claude/skills` 与 `.codex/skills` → `../skills` 软链、缺什么就生成 profile 模板、`.gitignore` 补 `.team-ledger/`、执行 `.githooks/install.sh`、写 `.team-kit.json` | 工程里的内核文件有未提交改动时拒绝（`--allow-dirty` 明确放行） |
| `sync <工程>` | 内核更新后同步到工程 | 同上；另外，工程里改过内核文件（与 `.team-kit.json` 记录、与 kit 都不同）时拒绝，`--force` 覆盖 |
| `check <工程>` | 逐个核内核文件（缺失 / 不一致 / 可执行位 / 内核目录里多出的文件）、软链、工程配置的节名与未填占位、`project.conf`、`core.hooksPath`、`.gitignore`、`.team-kit.json` 的来源提交 | 不一致退出 1 |
| `diff <工程> [路径]` | 打印工程相对内核的差异 | — |
| `adopt <工程> [路径] [--force]` | 把工程里改过的内核文件（含内核目录里新增的）拷回 `template/` | kit 在该工程上次同步之后也改过同一文件时，以同步时的 kit 版本为基线三方合并，改到同一处则拒绝；要收回的文件在 kit 里有未提交改动时拒绝；工程里删掉的不在 kit 里删，只提示 |

所有命令都**不提交**，由工程侧或 kit 侧核对后自行提交。

### 3.3 提交钩子里的内核提醒

`pre-commit` 的检查：暂存的内核文件内容与 `.team-kit.json` 记录的摘要不同、或被删除时，打印提醒，提示用 `bin/kit adopt` 收回。**只提醒，不拦。** kit 同步带来的提交与记录一致，不会提醒。

### 3.4 改内核的流程

1. 在 kit 的 `template/` 里改，跑三套测试（见第六节）。
2. 在 kit 提交、推送。
3. 对每个工程 `bin/kit sync <工程>`，在工程里提交（含 `.team-kit.json`）。
4. `bin/kit check <工程>` 退出 0。

工程里先改了的：在 kit 里 `bin/kit adopt <工程>`，然后按上面流程走。

## 七、使用方（各工程 SA）怎么配合

- **不在工程里直接改内核文件**。发现缺口时，在本工程账本落一条基建工作项（`--version _infra`），写明要改哪个内核文件、为什么改，然后报给 kit 维护方。
- 确有必要先在工程里改（比如值守时顺手修正契约错字）：提交时钩子会提醒。由维护方在 kit 里执行 `bin/kit adopt` 收回，再同步到所有工程。
- kit 发布更新后，维护方或各工程 SA 执行 `bin/kit sync <工程>`，核对后在工程里提交，并跑 `bin/kit check`。
- 工程专属信息（目录、命令、端口、部署、项目规范）只改工程里的 `docs/rules/工程配置.md`、`docs/rules/UI设计规范-本工程实例.md` 和 `.githooks/project.conf`，不需要经过 kit。

### v0.6.0（2026-11-07，prism 账本报的契约缺口）

**问题**（prism 账本 `并行线共用暂存区`，2026-11-06）：同一工作树里并行的两条线共用一个 git 暂存区，一方先暂存、还没提交的改动，会被另一方不带路径的 `git commit` 一并提交走。实例：prism 的 I2 提交 `6e9d7e5` 带走了 I1 已暂存的 124 个删除和 2 个迁移（内容最终正确，但归属不清，未改写历史）。原规则只要求「只 `git add` 自己的路径」，挡不住这种情况。

**改动**：
- `AGENTS.md`「多角色同 worktree 下的提交纪律」：**提交一律带路径** `git commit -m "…" -- <本次全部路径>`；新文件先 `git add`，删除直接写路径，改名新旧路径都写；提交后 `git show --stat HEAD` 核对；不替别人取消暂存。
- 契约 §三「同角色并行」、`roles/ui.md` 的提交纪律引用这一条。
- `bin/kit sync` 结束时打印现成的带路径提交命令（只含本次同步动到的路径）；README 的改内核流程同步改。
- 钩子测试新增 3 项，固定「带路径提交只带走、只扫自己的路径，别人暂存的内容原样留着」。

**实测依据**（临时仓库，git 自带行为）：带路径提交只含列出路径的修改 / 新增 / 删除；别人暂存的删除、新文件、含口令的文件都原样留在暂存区，提交钩子也不扫它们；未跟踪的新文件直接写进路径会报错；改名只写新路径时，旧路径的删除留在暂存区。

### v0.7.0（2026-11-07，工程 SA 报的账本缺陷）

**问题**：一个工作项由主线 SE 推进，旁边另有子任务（如 PM 澄清某个子产物）。子任务一落「交接」，`stale` 就不再显示这个工作项，主线 SE 明明还在跑。实际发生过一次：I5 上 PM 06:01 落了「交接」，I5 从 `stale` 里整项消失。根因：`_closed_items()` 只看工作项最新一条事件，是终态（「完成」或「交接」）就判整项收口，`cmd_stale()` / `cmd_owner()` 随后折叠该项所有角色的非终态行。

**改动**（`skills/team-ledger/`）：
- 能让整项收口的只有「完成」（`ITEM_CLOSING`）；「交接」仍是行级终态（这一行不计入停滞），但不再收口整项。
- 新增 `--part <子产物名>`：行按 `(role, item, part)` 独立存活，显示为「工作项/子产物」；子产物事件不参与整项收口；主线「完成」时连同子产物行一起收口。空白 `--part` 硬拒。
- 新增 4 组判据，含反向判据「主线进行中 ＋ 另一角色交接 ⇒ 主线仍在 stale 里」。
- `DESIGN.md`、`SKILL.md`、契约「附：状态账本」写明：同一工作项内并行的子产物，落账必须带 `--part`。（建议原文说补在契约 §三；账本用法在契约里集中写在「附：状态账本」，所以放在那里。）

**对存量的影响**：用新旧两版脚本读 vista / prism 的真实账本，`stale --hours 0` 与 `owner` 的输出和退出码逐字节相同（vista 8 / 8 项，prism 16 / 9 项）；按新规则也没有多冒出的行。改动只影响此后的「交接」与带 `--part` 的落账。
