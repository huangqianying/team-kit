# 版本进度汇报

**汇报必须来自账本与已提交产物，不凭记忆。** SA 采信各角色自报的测试数字，只核产物已提交、`commit:path` 可读，不复跑产品测试（契约 §五）；汇报须区分角色自报与 SA 所核范围。

## 一、取数（先跑完再动笔）

**以下命令以仓库根为工作目录。** 测试结果从负责角色的交付与证据中读取，未提供则写明缺失。

```bash
# 版本定位。system-version.json 是唯一真值源（受 git 跟踪）。
cat system-version.json

# 当前态 ＝ 全部非终态项，每行带接续方与卡点
python3 skills/team-ledger/team-ledger.py stale --hours 0
# 退出码：0 无非终态项 · 1 有 · 2 有项判不了（ts 脏）——2 不许当 0 写成「全清」
echo "RC=$?"

# 卡在产品负责人手上、只能等人的
python3 skills/team-ledger/team-ledger.py owner; echo "RC=$?"

# 代码落点
git rev-parse --abbrev-ref HEAD
git log --oneline main..HEAD                          # 空 = 零提交，全在工作区
git -c core.quotepath=false status --short

# 读取负责角色指定的已提交产物；路径与提交号取自交付
# git show <commit>:<path>
```

> **账本只有三条命令**：`append` / `stale` / `owner`。`show` / `log` / `verify-artifact` **不存在，不要调用**。
> **取证按契约 §三「取证口径」执行**，汇报明确所核产物及其版本。
> **汇报里不要写「锚点 RC=0」** —— 没有产出那个数字的命令。

## 二、输出结构

### 2.1 逐阶段逐步骤

按契约 §二 的对应链路列阶段，**已完成的也要列**——产品负责人需要看到全貌，不是只看当前点。每阶段一张表，列：步骤 / 执行角色 / 状态 / 判定 / 轮次 / 证据指针。

**阶段与步骤的唯一来源是契约 §二「标准链路」，本文不留副本。** 先按 §二.1 判这个工作项走的是快速链路还是全链路，再按对应那张表逐步骤报。 出报告前先读：

```bash
sed -n '/^## 二、标准链路/,/^## 三/p' docs/rules/团队协作契约.md
```

照读到的内容逐阶段逐步骤展开，**不凭记忆列、不自造**。角色与步骤改动时契约是唯一真值源——
本文若也抄一份，两处必然 drift 且无任何信号（六角色收敛为四角色时这份副本就漂了一次）。

状态符号：`✅` 完成 / `🔵` 进行中 / `⬜` 未启动 / `⚠️` 有问题（未完成、被跳过、结论过期）。

**工作项被明确裁剪的步骤照列并说明原因**；以现行链路为准，不恢复已取消的评审或签字步骤。

### 2.2 开发阶段进入代码开发后，展开到 task 子步骤

只要 `开发(SE)` 这一步已开跑，就必须再给一张 task 表。**任务清单以技术方案的任务表为准，不自造划分。**

| task | 内容 | 子步骤 | 状态 | 证据 |
|---|---|---|---|---|
| A1 | … | 写失败测试 → RED → 实现 → GREEN → 定向回归 | ✅ | 账本 note + 测试数 |
| B4 | … | （同上，标出停在哪一步） | 🔵 | — |

子步骤取值按 spec 里该 task 的 checklist，通常是 **写失败测试 → 跑 RED → 最小实现 → GREEN → 定向回归**；零改造链路则是 **建 GREEN characterization → 有效变异证明能红**。

**子步骤粒度的取证顺序**：

1. SE 账本 note（最可靠，但通常只到 task 粒度）
2. `git log main..HEAD` 的提交边界（spec 若规定一 task 一提交，提交即完成信号）
3. 工作区文件与测试结果（能证明"做了"，不能证明"按 TDD 顺序做的"）

**取不到就标 `证据不足`，不要填推测值。** 不能从当前测试通过推断实现前已跑过 RED；汇报照实说明证据范围，不新增开发门核证。

## 三、必须单列的三块

进度表之外，另起小节，不要混进表格：

1. **未完成/被跳过的项** —— 含被产品负责人裁定跳过的（如某项前置核对），标明已登记为技术债还是仍在欠账
2. **风险** —— 会影响下一步的事实。典型：零提交（工作只在工作区、按 task 回滚失效）、某角色卡住导致下游进不去、结论已过期
3. **等产品负责人处置的** —— 逐条列，别埋在正文里

## 四、硬规则

- **控制面不可信，产物才可信。** 报某步骤完成前，核它的产物与锚点；报某 agent 未开工前，核账本与工作区。失败信号与成功信号适用同一核证标准——不因「报的是失败」就免于核产物。
- **测试数字注明负责角色与证据指针**；缺证据如实说明，不由 SA 复跑补数。普通描述性数字不另设计数或重复核证要求。
- **退出码 0 只证明它所检的那一件事。** 别把一条检查的 RC=0 说成「已核」—— 一个核证器的射程常比它的名字小 —— **名字叫「三核证器」的脚本可能只读一份文件**。汇报里写清**核的是什么、没核什么**。
- **评审结论照实写。** 每份产物最多一轮评审（**轮次封顶 1**，契约 §五）；`CR` **不阻断**下一步，故报进度时要写明被评方「采纳 / 不采纳」—— 不写「已通过」把过程抹平。
- **自己判错过的结论，在汇报里更正**，不留着让产品负责人按错误事实决策。
