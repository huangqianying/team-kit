# UI 形态设计 Skill

## 核心原则

**下面这套设计思路是「原型该怎么搭」与「PM 该怎么审原型」的共同口径。**

- ✅ 每个页面类型（列表页/表单页/详情页/操作弹窗）**在动手前先定案**区域划分和组件选型
- ✅ 每个带复杂交互信号的场景（树形/状态机/批量/向导/权限矩阵）都有具体呈现方案，**且在原型里点得出来**
- ❌ **原型不得脱离 PRD 与 `UI设计规范.md` 自由发挥** —— 界面上凡属「什么必须成立」的，去 PRD 找；没写的，**报 PM 立进 PRD 作 AC，不要在原型里按自己的读法定下来**

**本 skill 不产出高保真视觉稿。** 它要求的是「**可被机械复核的形态**」——区域、组件、状态、档位（A 档不渲染 / C 档置灰 ＋ 具体原因）都要能被一条命令或一次渲染核出来。

## 产物的质量口径（**与生产代码不同，读两遍**）

**原型是一次性产物，不长成产品前端**；产品前端由 SE 在阶段 2 之后另写。

- **要**：`typecheck` 与 `build` 绿（编译不过 ⇒ 人打不开 ⇒「快速看效果」为 0）＋ **形态断言**（入口集 · A/C 档 · 列集 · 多值不丢 · 空态）
- **不要**：覆盖率要求 · 集成测试 · 任何对后端行为的断言（**没有后端，那种测试是假的**）
- **要保住的三样是一切取舍的标准**：**快速修改 · 快速看效果 · 快速确认**

原型的启动与自检命令见 `docs/rules/工程配置.md`「命令」，组件库与原型主题见同文件「项目规范」。

> 角色与闸门：本 skill 的执行者为 **UI**（产出原型）与 **PM**（按同一套口径审原型）。原型经 **PM 审查**（需求符合性 ＋ 规范符合性，一轮、建议级，结论落账本）后，**由产品负责人确认形态（唯一固定人工闸门），无人代签**；技术可行性有争议时交 SA 裁定。全链路必出原型（契约 §二.4 阶段 1）；增量链路只在涉及新页面或新交互形态时出（契约 §二.3 第 1 步）；快速链路不出原型。角色职责与协作链路见 `docs/rules/团队协作契约.md`。

## 输入要求

**依据恰两份，没有第三份**：

- **SA 指定版本的需求文档**（`docs/prds/<版本>/`，由 PM 产出）——含页面/功能、角色权限、验收标准，以及标注为「复杂交互」的条目。
- **全局 UI 设计规范** `docs/rules/UI设计规范.md`（通用规则）＋ `docs/rules/UI设计规范-本工程实例.md`（本产品的取值）——全局视觉/交互规则的事实源。

**需求文档未出就不开工** —— 阶段 1 的顺序是「需求文档(PM) → 原型(UI)」；边写边改需求会让形态失锚。提示：
> "请先让 PM 出需求文档并由 SA 指定依据版本。若需求分析尚未完成，先由 PM 走 `requirements-analysis` skill。"

**以派活方指定的需求文档版本为依据**；原型上的改动按**需求改动**处理 —— **先改需求文档，再改原型**（契约 §五），取证依契约 §三。

## 工作流程

```
读取 PM 需求文档 + 全局 UI 设计规范（docs/rules/...）
        ↓
【Step 1】对齐全局令牌：色彩/排版/间距/圆角材质/动效/暗色 + 通用交互（以 docs/rules 令牌体系为准，缺项交 SA 协调 PM）
        ↓
【Step 2】页面类型布局模板：按列表页/表单页/详情页/操作弹窗分别定义
        ↓
【Step 3】复杂交互专项设计：逐一处理需求文档标记为复杂交互的场景，在原型里真实流转；有备选方案的，做成可切换的两版
        ↓
【Step 4】产出原型并交付：代码落 `prototypes/<版本>/`，形态断言落自测试，交付说明落 docs/reviews/<版本>/
        ↓
PM 原型审查（一轮）→ 产品负责人确认形态（无人代签）
```

## Step 1：对齐全局令牌与交互规范

**全局视觉/交互标准以 `docs/rules/UI设计规范.md` 为准，本 skill 不重复定义、不自带默认取值。** 本步只做两件事：① 把本次需求涉及的页面逐项对到全局规范的令牌与规则上；② 若全局规范确缺某项，交 SA：属于本产品取值的由 PM 补进 `docs/rules/UI设计规范-本工程实例.md`，属于通用规则的由 SA 报 team-kit 维护方改内核，更新后再使用；UI 不自行改规范——**不得在原型里另立一套色值/字号/圆角**。

### 令牌体系（一律引用全局规范 §1 定义的 CSS 变量，禁止硬编码）

设计决策全部落到全局规范 §1–§6 的设计令牌，逐组对齐、不自造：

| 令牌组 | 对齐到全局规范 | 铁律 |
|------|------|------|
| 色彩 | §2 色彩系统（accent = System Blue、语义色、中性灰、§2.4 语义化令牌层） | 组件**只引用 §2.4 语义化令牌**；结构性装饰色 ≤3 且取自 §2.5 数据可视化色板 |
| 暗色 | §2.4 / §2.6 主题切换 | **暗色是一等公民**，每个颜色都要亮/暗两套值，不得只做亮色 |
| 排版 | §3（字体栈、§3.2 字号阶、§3.3 数字排版） | 数字用等宽/表格数字，不逐页自定字号 |
| 间距/栅格 | §4 间距与栅格 | 用间距令牌，不写魔法数 |
| 圆角/材质 | §5（连续圆角、§5.2 Elevation、§5.3 磨砂、§5.4 发丝线、§5.5 玻璃表面） | 层级靠材质+光影，不靠到处画 1px 边框 |
| 动效 | §6（§6.1 曲线/时长令牌、§6.2 微交互、§6.4 无障碍降级） | 动效引用令牌；必做 `prefers-reduced-motion` 降级 |

### 通用交互模式（以全局规范为准，本表只做对齐索引）

| 场景 | 对齐到全局规范 |
|------|------|
| 加载态 | **骨架屏优先（§13.2）**——列表/详情用骨架屏，而非全屏加载遮罩；按钮提交中禁用 + loading |
| 空状态 | 全局规范空状态样式，文案格式："暂无[业务对象]" |
| 错误提示 | 表单校验错误字段下方（§15.3）；接口业务错误按项目错误码规范提示（若尚未定义，交 SA 协调明确口径） |
| 二次确认 | 破坏性操作（删除/停用等）必须二次确认，文案："确定要[操作]吗？[后果说明]"（§16 弹窗） |
| 查询触发 | 遵守项目 Enter 查询规则；查询栏用 §12 `.filter-bar` + filter-pill 回填 |
| 表单校验 | 字段下方，实时校验（blur 触发）+ 提交时统一校验（§15.3） |

## Step 2：页面类型布局模板

对每种页面类型给出统一的区域划分和组件映射，所有同类型页面遵循相同布局骨架，仅内容字段不同。组件以本工程组件库为准（见 `docs/rules/工程配置.md`「项目规范」），下表写通用组件类型，按组件库落到对应组件（例如组件库为 Element Plus 时，表格即 `el-table`）；通用列表/分页/空状态用项目已有的统一组件。

### 列表页

| 区域 | 内容 | 组件 |
|------|------|------|
| 顶部操作区 | 主操作按钮（新建/导入/同步等） | 按钮 |
| 筛选区 | 按需求文档中标记为"筛选"的字段 | 行内表单 + 下拉/日期选择/输入框 |
| 内容区 | 数据表格 | 表格 + 统一空状态组件 |
| 分页区 | 分页控件 | 项目统一分页组件 |
| 行内操作列 | 按业务状态 + 权限条件显示/隐藏 | 文字按钮 |

### 表单页

| 区域 | 内容 | 组件 |
|------|------|------|
| 表单区 | 按需求文档输入字段生成，必填标红星 | 表单 + 对应输入组件 |
| 校验提示 | 字段下方 | 表单项内置校验 |
| 底部操作区 | 提交 / 取消 | 按钮 |

### 详情页

| 区域 | 内容 | 组件 |
|------|------|------|
| 基本信息区 | 只读字段展示，空值显示 "-" | 描述列表 |
| 状态标识 | 与业务状态一致的颜色标签 | 标签 |
| 操作区 | 按业务状态 + 权限条件显示的操作按钮 | 按钮 |
| 关联内容区 | 关联数据（明细/记录等） | 表格 / 时间线/图表组件 |

### 操作弹窗

| 区域 | 内容 | 组件 |
|------|------|------|
| 标题区 | 操作名称 | 对话框标题 |
| 内容区 | 表单或确认文案 | 表单 / 纯文字 |
| 底部操作区 | 确认（loading + 禁用）/ 取消 | 按钮 |

> 页面与组件命名约定见 `docs/rules/工程配置.md`「项目规范」。设计时须对照需求文档的角色权限，逐角色写清同一页面对不同角色显示什么、可操作什么。

## Step 3：复杂交互专项设计

对需求文档标记为复杂交互（树形/状态机/批量操作/多步骤向导/复杂权限矩阵）的每个场景逐一处理，**不得跳过**，且**在原型里真实流转**（点得开、关得掉、状态变得了）。

### 各信号类型的设计要点

| 信号类型 | 设计要点 |
|---------|---------|
| 树形层级 | 用树组件展示层级；根节点操作入口在工具栏，子节点操作入口在节点右键菜单或悬浮操作图标；不同层级的可操作项按节点类型/层级条件渲染 |
| 状态机 | 用标签/步骤条标识当前状态；操作按钮按当前状态条件渲染；状态流转需二次确认的动作要有对应弹窗 |
| 批量操作 | 列表页表格增加多选列；选中后底部/顶部浮现批量操作栏，显示"已选 N 项"；批量提交前二次确认，展示批量操作范围 |
| 多步骤向导 | 用步骤条展示步骤进度；每步校验通过才能进入下一步；支持回退到前置步骤，回退不清空已填数据 |
| 复杂权限矩阵 | 页面元素（按钮/字段/整个模块）的显示与否严格对照需求文档的角色×功能矩阵，同一组件针对不同角色渲染不同的可操作范围，不用前端硬编码判断，统一走权限工具函数 |

**有备选方案的场景**：两版都做进原型、用开关切换，不写文字比较 —— 产品负责人在屏幕上选。

## Step 4：产出原型并交付

按 Step 1–3 的布局与交互方案实现原型，运行编译与形态断言后交 SA 安排 PM 审查（一轮），再由产品负责人确认形态。

确认时给出可运行的原型及需取舍的关键判断点：复杂交互的选定 / 备选方案及切换方式、全局规范尚未固定的开放项。规范已固定的强调色、字号、圆角等不另设确认步骤。

产品负责人提出调整时，按反馈修改；涉及需求变动先交 PM 更新 PRD，再改原型。产品负责人未明确确认前，不把形态记为已确认；PM、UI、SA 均不能代签。

## 产出规范

### 产出：`prototypes/<版本>/` 下的 Web UI 原型，**不产出散文规格文档**

Step 1–4 定出来的布局模板与专项设计是**给原型用的口径**，**不另写一份文档去描述它们** —— 同一件事两个事实源，必然分叉。它们的落点是代码与断言：

| 产出 | 落在哪 | 验收它的东西 |
|---|---|---|
| **原型代码** | `prototypes/<版本>/` | `typecheck` 与 `build` 绿 |
| **形态断言** | 当前版本目录的自测试 | 入口集 · A/C 档 · 列集 · 多值不丢 · 空态，**逐条可跑** |
| **交付说明** | `docs/reviews/<版本>/` | 本轮完成项 · 关键验证证据 · 本宿主核不了什么（**明写**，不假装核过） |
| **版本清单** | `prototypes/README.md` | 该版本一行：状态（当前 / 冻结）· 确认提交 · 需求依据 · 交付说明 · 访问地址 |

**版本目录**：新版本从上一版目录复制成 `prototypes/v<版本号>/` 再改；只改当前版本的目录；版本放行后目录冻结。旧版本形态到对应目录里看，不在新版本里叠加阶段开关。

**交付说明写什么、不写什么**：

- **写**：这一轮做了哪几项（对到派活范围）· 影响形态通过的关键验证证据 · **本宿主量不到的东西**（如 jsdom 量不到几何）明写「须换宿主复量」或「本门不覆盖」。
- **不写**：页面区域划分的散文描述（看代码）· 组件选型的理由长文（看规范）· 任何对后端行为的断言（**没有后端**）。

**断言要落在「效果」上，不是落在「为达成效果而写的那条规则」上。** 判法一问：**这条断言为真、而我要保的事情为假 —— 可能吗？** 可能 ⇒ 它断错了对象。宿主量不到结果时，断言会无声退化成断言作者意图。

## 常见陷阱与应对

| 陷阱 | 表现 | 应对方式 |
|------|------|---------|
| 跳过专项设计 | 复杂信号场景只套用通用页面模板 | 检查：需求文档标记为复杂交互的场景是否都在原型里点得出来 |
| 布局模板过粗 | 只写"表格+分页"，没有说清楚筛选区/操作列的条件渲染规则 | 对照具体验收标准，补充条件渲染细节 |
| 权限设计与矩阵脱节 | 只写了"按权限显示"，没有对照需求文档权限矩阵具体到角色 | 逐条对照权限矩阵，写明哪个角色看到什么 |
| 与全局规范重复/冲突 | 原型里重抄一遍全局视觉规则，或和 docs/rules 打架 | 全局规则只引用不重抄；缺项交 SA（本产品取值 → PM 补本工程实例；通用规则 → 报 team-kit 维护方） |
| 另立一套视觉令牌 | 在原型里自定色值/字号/圆角，或纠结像素级间距 | 一律引用全局规范 §1–§6 令牌（规范 §1 的 `:root` 变量），缺项交 SA 协调 PM，不自行改规范 |
| 把口径另写成一份文档 | Step 1–3 的布局模板与专项设计被抄成一份散文规格，与代码并存 | **同一件事只留一个事实源** —— 口径落代码与断言，交付说明只记射程与命令 |
| 原型与既有页面骨架不一致 | 同类页面在产品里已有骨架，原型另起一套 | 先读产品前端的同类页面（位置见 `docs/rules/工程配置.md`「目录」） |
| 只做亮色 | 只在亮色下做和看，暗色没逐面核 | 切暗后逐面看 |
| 跳过形态确认直接定稿 | 原型审查后未交产品负责人就自行定稿 | PM 审查后必须由产品负责人确认形态 |
| 备选方案敷衍了事 | 复杂交互只做选定方案，备选方案随便凑一个明显更差的 | 备选方案要是真的可行方案，做进原型供产品负责人比较选择 |

## 完成后

- 确认**原型代码已落 `prototypes/<版本>/`**，`typecheck` 与 `build` 绿，形态断言逐条可跑；交付说明已落 `docs/reviews/<版本>/`（落位/命名以 `manage-docs` skill 为准）。
- 若 Step 1 发现规范缺项，确认已交 SA 协调 PM 处理，不由 UI 自行回写规范。
- 交 **PM 原型审查**（需求符合性 ＋ 规范符合性）→ **产品负责人确认形态**（唯一固定人工闸门，**无人代签**）；技术可行性有争议时交 SA 裁定。
- **原型不得被引为任何 AC 的通过证据** —— 它是**形态**的事实源，不是**行为**的证据。产品前端是另一份产物，由 SE 在阶段 2 之后另写。
