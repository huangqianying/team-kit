# 团队协作状态账本设计

> 定位：本文是契约 `docs/rules/团队协作契约.md`「附：状态账本」的具体形态与落地设计，工具是同目录的 `team-ledger.py`（用法见同目录 `SKILL.md`，本文不复述命令）。账本是开发团队的协作管理抓手，记的是「谁在做、做到哪一步」，与产品自身的业务数据无关。

---

## 一、射程

PM / UI / SE / QA 是 SA 值守会话的 **subagent**：任务由 SA 直接派出，可能同步返回，也可能需要等待异步结果；结论由父会话收齐。**账本不负责唤醒或派活**，不是跨会话的消息总线。

需要持久化的依据是 **SA 的上下文会被压缩，或因额度耗尽换宿主、换会话接班**。压缩 / 换端之后，「停在哪、谁欠谁一棒、哪件事在等人裁」不能依赖旧会话的记忆或子任务标识；账本和已提交产物共同支持接班。

射程按这个依据裁，恰好三条命令：

| 命令 | 答的问题 | 为什么别处答不了 |
|---|---|---|
| `append` | 把状态写进唯一的事实源 | — |
| `stale`（`--hours 0` 即当前态） | 谁停太久 / 现在全局停在哪 | 状态散在各角色产物与会话里，要逐份读，且会话会被压缩；账本一行就给 |
| `owner` | 哪些事卡在产品负责人手上 | 别处没有这个队列 |

### 不要的命令，及理由

| 不要 | 理由 |
|---|---|
| `verify-artifact` / `verify-candidate`，及 `--artifact` / `--at` / `--candidate` / `artifact_sha` / `review_sha` / `candidate_sha` | 产物版本及证据由契约「派活」的取证口径与「评审与合入」的证据指针统一规定；账本只记录状态，不另设核锚字段和命令。留着一个没人核的锚，和一个正确的锚在账本里长得一模一样 |
| `--job` | 账本不派活，没有需要锚定的派活任务标识 |
| `show` / `render` / `.team-ledger/ledger.md` | md 是 jsonl 的**派生态**，一旦被人读、被文档引用，同一事实就有两个源。当前态由 `stale --hours 0` 现算现打 |
| `owed` | 判据与 `stale` 完全重合（非终态行即待派的棒）；`stale` 每行已带出接续方 |
| `items`（粒度自查） | 粒度判据在契约「附：状态账本」；语义重复（中英互译、增删词）机器挑不出 —— 实测真重复项相似度 0.49、合法异项 0.90，模糊阈值必然误伤。工具只做确定性归一（见 §三 `item`） |
| `archive` / `set-version` / `log` | 历史只增不减，`完成` 的项自然沉默，不需要归档动作。版本**只读** `system-version.json`：`.team-ledger/` 不入库，版本号存在那里只存在于本机 |

## 二、形态：只有事件流

| 层 | 文件 | 性质 | 说明 |
|---|---|---|---|
| **事实源** | `.team-ledger/ledger.jsonl` | 追加式事件流（运行时，不入库） | 每次状态变更**追加一行 JSON**（`O_APPEND`，行 < PIPE_BUF 原子），并由 `.team-ledger/ledger.lock` 的 `flock` 互斥 |
| **当前态** | 无文件 | 现算 | 每个 `(role, item)` 取**最新事件** = 当前态，由 `stale --hours 0` 打印。**不落第二份文件** |
| **版本真值源** | `system-version.json`（主工作树根） | **入 git** | `append` 据此给事件打 `version` tag；读不到则落 `_infra` 并告警。本工具**只读不写** |
| **工具** | `skills/team-ledger/team-ledger.py` + `SKILL.md` | 入 git | 原子追加 + schema 强校验 + 两条巡检。`.claude/skills` 与 `.codex/skills` 软链至 `skills/` |
| **判据** | `skills/team-ledger/test_team_ledger.py` | 入 git | `python3 skills/team-ledger/test_team_ledger.py`，全程用 `TEAM_LEDGER_DIR` 隔离到临时目录 |

**环境变量**（测试与隔离用）：`TEAM_LEDGER_DIR` 覆盖账本目录；此时版本真值源默认取该目录下的 `system-version.json`。`TEAM_LEDGER_SYSTEM_VERSION` 直接指定版本真值源文件。

**为什么事件流当事实源**：让多 agent 就地改一张 markdown 表是读-改-写竞态（会串写 / 覆盖）。「只追加、当前态派生」把写路径退化为单行原子追加，并发安全且零协调；当前态是纯函数派生，随时可重算，且免费带来完整历史。

**账本落唯一主工作树**：`.team-ledger/` 是不入库的工作区目录，每棵 git worktree 各一份。工具按 git common-dir 解析主工作树根来定位账本，任一 worktree 调用都写同一本账、读同一版本，杜绝每棵 worktree 各持一本账的分叉。脚本自身路径用 `realpath` 解析（`.claude/skills` 是指向 `skills/` 的软链，两条调用路径必须算出同一个仓库根）。

**读侧容错**：坏行（非 JSON）跳过、不阻塞读账；未知字段忽略。故同 schema 的存量账本可原样迁入。

## 三、事件 schema

一行 JSON，字段：

| 字段 | 必填 | 取值 |
|---|---|---|
| `ts` | 自动 | 落账时间（`YYYY-MM-DD HH:MM`；默认东八区，`TEAM_LEDGER_UTC_OFFSET` 可改） |
| `version` | 自动 | 取自 `system-version.json`；`--version` 可显式覆盖；读不到为 `_infra` |
| `role` | 是 | 枚举：`pm` / `ui` / `sa` / `se` / `qa` |
| `item` | 是 | 工作项短标识；同一工作项跨状态**保持同名**。同一 `role` 内，大小写 / 空格 / 连字符 / 下划线 / 全角差异视为同事异名、硬拒并提示既有原名；确属另起一项加 `--force-new-item` 并在 `--note` 写明理由 |
| `part` | 否 | 子产物名：同一工作项内并行推进的子产物（如主线 SE 开发时 PM 澄清其中一份）。行按 `(role, item, part)` 独立存活，`stale` / `owner` 显示为 `工作项/子产物`；子产物的事件**不参与整项收口** |
| `phase` | 否 | 枚举（标注链路环节）：`requirement` / `design` / `ui-design` / `ui-proto` / `spec` / `plan` / `dev` / `ui-review` / `test-design` / `test-case` / `test` / `accept` / `review` / `deploy`（中文门名自动归一）。`ui-proto` 是 UI Web 原型（「UI设计」「界面设计」「原型」等中文门名都归到它）；`ui-design` 为兼容存量行保留，须显式写 slug |
| `status` | 是 | 枚举：`进行中` / `待评审` / `评审中` / `阻塞` / `完成` / `交接`。终态 = `完成` / `交接`（行级：这一行不再计入停滞）；能让**整项**收口的只有 `完成` |
| `to` | 条件 | 接续方角色；`status=交接` / `待评审` 时**必填** |
| `blocker_role` | 条件 | 被卡方角色；`status=阻塞` 时**必填**。等产品负责人裁定写 `owner`，进待裁决清单 |
| `blocker` | 条件 | 卡在什么；`status=阻塞` 时**必填** |
| `round` | 否 | 评审轮次。契约「评审与合入」定**轮次封顶 1**：每份产物最多一轮评审，按同一 `item` 计 —— 换个名字就能重开一轮，所以 `item` 的同名硬拒是承重的，不是洁癖 |
| `decision` | 否 | 枚举：`APPROVED` / `CR` |
| `review` | 否 | 存量评审记录的索引，新工作项不用：契约「评审与合入」规定评审结论只落账本，不写评审记录文件 |
| `forced_new_item` | 自动 | 用了 `--force-new-item` 即留痕，可 grep 审计 |
| `note` | 否 | 一句话说明。**判定不要塞进 note**，用 `decision` 字段才统计得到 |

枚举字段一律**强校验**，非法值直接退出**且不落账** —— 校验不通过还落账等于让账本进脏数据。

## 四、协作协议

**落账（全员，每次状态变更即记）**：开工 `进行中`、求评审 `待评审`（必带 `--to`）、评审 `评审中`（带 `--round`）、遇阻 `阻塞`（必带 `--blocker` 与 `--blocker-role`）、通过 `完成`、下派 `交接`（必带 `--to`）。**非终态必须指定接续方** —— 它只是给 SA 看的状态标记，**落账不唤醒任何人**；棒由 SA 读账本后主动派出，角色不得绕过 SA 自行调度（契约「派活」）。

**SA 读账**：每回合先 `stale`、再 `owner`，步骤与退出码见 `SKILL.md`「SA 值守的每回合三步」「读账」。退出码是承重的：`stale` 退 0 才是「确无停滞」，`ts` 脏到判不了退 2 —— 判不了 ≠ 全清；`owner` 退 1 = 有待裁决。

**收口语义落在 item 上**：某 `item` **主线**（不带 `part` 的事件）的最新事件为 `完成` 时，该 item 下其他角色仍停在非终态的行（含子产物行）折叠、不计入停滞（「完成」通常只由收口方落一行）。完成后再落非终态即视为重新开工，逐行恢复可见。

- **`交接` 不收口整项**：交接只代表一棒传了出去，整件事未必结束。曾按「最新事件为终态」收口，子任务一落 `交接`（如 PM 澄清完交回），主线 SE 仍在跑的 `进行中` 也被折叠，`stale` 里整项消失。
- **子产物用 `--part`**：同一工作项内并行推进的子产物，子线落账带 `--part <子产物名>`。它只管自己那一行：子产物的 `交接` / `完成` 只让这一行退出停滞视图，不影响主线；主线 `完成` 时连同子产物行一起收口。

## 五、生命周期

- 账本是**团队级、跨会话长存**的，不随单次开发会话重置。
- `完成` 的工作项不进 `stale`、不进 `owner`，自然沉默，无需归档动作。
- 没有归档命令。历史全在 `.team-ledger/ledger.jsonl` 里只增不减；真要瘦身是人工的事，且**瘦身即丢历史**，须经产品负责人决定。

## 六、边界

- 账本记录的是**开发团队的协作状态**，不是产品的业务数据。
- 账本不替代角色产物（需求文档、设计、spec+plan、方案+用例、测试报告）；它是**状态索引**，指向而不复制那些产物。评审结论只落账本（`--decision` ＋ `--note`）。**DoD ＝ 产物已提交 ＋ 账本落终态**（契约「评审与合入」）。
- 两类工作分账：产品开发带产品版本号；工程基建带 `--version _infra`（见 `AGENTS.md`）。
- **不在射程内的别往回加**。`test_team_ledger.py` 里有两组反向判据，钉住 9 个不要的子命令（`show` / `render` / `log` / `owed` / `items` / `archive` / `set-version` / `verify-artifact` / `verify-candidate`）与 4 个落锚参数（`--artifact` / `--at` / `--candidate` / `--job`）必须报错 —— 要加回来，先改那两条判据。
