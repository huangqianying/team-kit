# 技术评审（执行者：SA）

> **适用**：spec + plan 一份文档（契约 §二.3、§二.4）、测试方案 + 用例一份文档（契约 §二.4）。系统设计由 SE 判可实现性、PM 判需求符合性（契约 §二.4），SA 不用本 skill 评自己写的系统设计。
>
> 评增量链路的 spec + plan 时，它同时承担系统设计检查：下表「设计部分」与「spec」「plan」三行一并适用。

评审范围、轮次与通过条件统一按 `docs/rules/团队协作契约.md` §五执行。本 skill 补充技术检查方法。

## 审查范围

- 完整阅读产物及相关上游依据，检查技术正确性、内部一致性、可实现性与需求覆盖。
- 评审一轮，修后不回评；发现按级别集中落账，不为一般问题或建议另开评审。

## 关键约束与引用

只对影响方案的关键约束、疑似矛盾和可疑的规范声明核对出处：

1. 定位原文，确认适用角色、范围与语义；不能把建议写成禁止、把运行时能力写成项目纪律。
2. 判断声明是否真的改变需求、权限、架构或执行方式。缺引用或行号格式本身不自动判 `CR`；真实的错误约束按其影响定级。
3. 关键约束缺依据、无法判断可行性或需求符合性时补核；需要作者作判断的内容明确写成判断及理由。规则生效时点影响结论时才查历史。

普通引用格式问题可批量补正，不要求逐处行号核验。

## 各类产物的检查重点

| 产物 | 检查重点 |
|---|---|
| 设计部分（增量链路 spec + plan） | 系统边界、数据模型、权限隔离、失败语义、依赖与可实现性 |
| spec | 与设计一致、接口契约、需求覆盖、关键不变量和边界行为 |
| plan | 依赖顺序、步骤可执行、验证方法、职责归属 |
| 测试设计 | 需求追溯、重要正反向及边界场景、测试隔离、判据能检出所声称的缺陷 |

## 结论

- 给出 `APPROVED` 或 `CR`，附影响通过结论的关键证据、阻塞问题及必要修正。
- `CR` 不阻断下一步，被评方自决修改并落账说明「采纳 / 不采纳 ＋ 一句理由」。
- 普通建议集中记录，不逐条立项；证据按契约 §三、§五执行，不为普通数字计数或强制两种取法。
- **结论只落账本**（`--decision` ＋ `--note`），**不写评审记录文件**（契约 §五）。随后按 SA 派活规则交接。
