# 讨论洞见账本 Skill

## 为什么需要这个 skill（它防的失败）

深度讨论质量很高，但**一到写文档就丢关键点**——因为：① 让**交付物的通用模板**当骨架、往里填，模板里没槽位的洞见就漏了；② 写作从「思考模式」切到「产出模式」，批判姿态掉线，文档变成**形式化转录**；③ 讨论与文档之间**没有显式的桥**，全靠记忆（有损）；④ 完成前不自检，于是**用户变成你的 QA**，替你逐轮捡回丢掉的洞见。

更隐蔽的二次失败：**账本本身只登「结论一行行」，把推理过程也丢了**——又一次用形式顶替实质。

> 修法：**显式账本 + 强制自检**，而非靠记忆和自觉。

---

## 核心铁律

1. **记「思考过程」，不只记「结论」。** 每个关键洞见要留下**起点问题 → 推理 → 结论**，以及**出处**（谁提的 / 怎么推出来的 / 是否一度漏了又补回）。只写结论 = 失败。
2. **账本是事实源。** 需求 / 设计文档必须**逐条承接**账本；账本不靠记忆，靠当场登账。
3. **文档完成前逐条自检。** 走账本每条：✅ 是否落成了 load-bearing 的内容（带验收标准的真需求，而非一句带过）、⏳ 是否标注待确认、🔭 是否归远期。核不过即为**欠账**，显式挂出来。
4. **insight-first，模板第二。** 先把账本洞见映射到文档落点，再用文档模板当**容器**保完整；**某条洞见没槽位就加章节，绝不为迁就模板而丢**。

---

## 何时创建 / 何时更新

- **创建**：**每个（需求 / 大特性 / 独立议题）的深度讨论展开时，单独建一份账本**，尽早建（不要等讨论完）；不同议题不要堆进同一个文件。
- **更新（活文档）**：每浮现一个关键洞见 / 决策 / 事实修正 / 待确认项，**当场追加一条**；每次写或改需求 / 设计文档后，回来更新「落点」与「状态」，并刷新「欠账」。
- 账本**版本随讨论演进**（v1.0 → v1.1 …），不追求一次写全。

## 结构规范

账本 = **上篇（思考过程）+ 下篇（决策追溯表）+ 欠账**。

### 头部元信息
文档性质、版本（活文档）、日期、编写角色、用途、**落点约定**（指明需求报告 / 设计文档等的路径，供下篇「落点」列引用）。并写一段**「为什么有这份账本、为什么记过程」**。

### 上篇 · 思考过程（本 skill 的重点，最易被省掉）

按**分析主题**分段，每段是一次推理，不是一句结论。每段建议含：

- **起点问题**：这段在回答什么问题。
- **推理**：怎么一步步想到的（可含对比、反例、被推翻的假设）。
- **结论**：推理落到什么决定。
- **出处 / 归属**：产品负责人提的 / 作者推的 / **一度漏了被追问才补的**——诚实标注，别美化。

必须保留的**两类内容**（最常被丢）：
- **反例与纠错**：被否决的设想、纠正过的误解——它们承载了「为什么不那样做」，价值极高。
- **「地基型」分析**：那种「后面大量需求都从这里推导」的根分析（如领域里的关键区别、核心权衡），要摊开成表/成段，不能压成一行。

> 检验：把上篇给一个没参与讨论的人读，他能否复现「为什么这么决定」？不能，就是又只记了结论。

### 下篇 · 决策追溯表

按主题分组的表，每条一行：

| 列 | 含义 |
|---|---|
| 编号 | D01、D02…（稳定编号，供文档引用） |
| 决策 / 洞见 | 一句话结论 |
| 出处 | 产品负责人 / 作者 / 评审 / 实测… |
| 状态 | ✅ 已定 ｜ ⏳ 待确认 ｜ 🔭 远期 ｜ 🔧 事实修正 ｜ 📌 元/过程 |
| 落点 | 承接到哪个文档的哪条需求 / 哪节；未落则空并进「欠账」 |

追溯表条目应**回指上篇对应的分析段**，让「结论 ↔ 推理」双向可查。

### 附 · 欠账清单
列出**尚未落进文档的洞见**、**待用户确认的 ⏳ 项**、**待定的机制问题**。这是自检的产物，必须显式化——不许沉默省略。

## 落位与命名（依 manage-docs）

- 目录：**`docs/insights/`（洞见文档专属目录）**——洞见账本跨需求/设计，独立成目录，不混入 `docs/prds`。
- **一个议题 / 大特性一份账本**，不把所有讨论堆进同一个文件（否则账本无限膨胀、主题混杂、难追溯）。
- 命名：`docs/insights/<议题slug>-洞见账本.md`（活文档，主题版本写在头部元信息；可加 `YYYY-MM-DD-` 前缀便于按讨论时间排序）。
- 具体归类 / 命名细则以 `manage-docs` skill 为准。

---

## 使用流程

1. **讨论中**：每得一个关键洞见 / 决策，立即在**上篇**补一段推理、在**下篇**补一行。
2. **写文档前**：以账本为 insight-first 的清单，逐条规划落点。
3. **写文档后**：逐条对下篇自检——落成 load-bearing？标了待确认？归了远期？刷新「落点」「状态」「欠账」。
4. **交评审时**：账本随需求 / 设计文档一并提交，评审方可据它核对文档完整性、理解决策来龙去脉。

## 与其它 skill 的关系

- 需求 / 设计文档（PM 角色产出的用户需求文档 / 需求规格说明书、TA 角色产出的设计文档等结论型产物）：本 skill 记**其背后的思考过程与追溯**，两者配套，账本防止文档丢洞见。
- `manage-docs`：账本的目录归属与命名依它。
- 本 skill **不替代**需求 / 设计文档，是它们的**底座与自检工具**。

---

## 反模式（出现即返工）

- ❌ 只登结论一行行，没有推理过程。
- ❌ 地基型分析（关键区别 / 核心权衡）被压成一句话。
- ❌ 丢掉被否决的设想与纠错（只留「正确答案」，抹掉「为什么不那样」）。
- ❌ 文档写完不对账本自检，让用户来发现遗漏。
- ❌ 为迁就文档模板的章节结构而丢洞见。

## 完成后自检清单

- [ ] 上篇每段能让局外人复现「为什么这么决定」？
- [ ] 地基型分析已摊开（表 / 段），非一行结论？
- [ ] 反例 / 纠错 / 被否决设想已保留？
- [ ] 下篇每条有 出处 / 状态 / 落点，并回指上篇？
- [ ] 已逐条对文档自检，「欠账」已显式列出？
- [ ] 待用户确认的 ⏳ 项已标注、未擅自当已定？
