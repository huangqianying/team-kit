# diff-impact：改动影响分析

**按需使用的方法，不是必经步骤。** 对一段改动做静态分析：它改变了什么行为、波及哪些调用方、有没有兼容性问题、该重测多大范围。**只读**：不改代码、不切分支、不落评审状态。

推荐在三处用（都是「可以用」，用不用由 SA 判断）：
- 判复杂度时，已有改动可分析的（契约 §2.1）；
- 合入并行线前看波及面（`docs/rules/并行线.md`「五」）；
- 验收修复后定复测范围（`docs/rules/并行线.md`「六」）。

## 一、输入与范围

| 给什么 | 分析什么 |
|---|---|
| 不给引用 | 当前未提交的改动（暂存 ＋ 未暂存 ＋ 属于本次范围的新文件） |
| 一个引用 | 该引用与 HEAD 两个提交快照的差异，不混入工作区改动 |
| 两个引用 | 第一个与第二个提交快照的差异，不混入工作区改动 |
| 某条线 `lane/<短名>` | 这条线带进来的改动：基准取 `git merge-base <集成分支> lane/<短名>`，目标取线分支的提交 |

**未提交模式**：
- 先 `git status --short`，再用 `git diff --no-ext-diff --no-textconv HEAD --` 取已跟踪文件的改动；
- `git diff` 不含未跟踪文件，用 `git ls-files --others --exclude-standard` 单独列出，只读明确属于本次范围的新文件；
- 范围混杂、说不清哪些属于本次时，先列出候选路径问清楚，不把整个工作区当成一次改动；
- 结束前再看一次 `git status --short`，改动有变化就重新分析，不交旧结论。

**提交对比模式**：
- 先用 `git rev-parse --verify --end-of-options '<引用>^{commit}'` 把每个引用解析成完整 sha，之后只用 sha；
- 取差异：`git diff --no-ext-diff --no-textconv <基准sha> <目标sha> --`。

**线的模式**：
- **不能直接对比集成分支头和线分支头**：那样会把集成分支上其他线已合入的改动，算成本线的反向改动；
- 基准用 `git merge-base <集成分支> lane/<短名>` 的结果，报告里写明实际用的基准 sha 和目标 sha。

**只读取证**：
- 读历史版本用 `git show <sha>:<path>`，搜历史版本用 `git grep <模式> <sha> --`；不切分支、不 reset，不拿工作区代替历史版本；
- 调用链和行号取自目标 sha；删除的代码取自基准 sha，并标明；
- 不读凭据、`.env` 一类文件，不读被忽略的目录和构建产物。

**停下来的情况**：引用无效、不在 git 仓库里、有未解决的冲突时，说明原因并停止。范围内没有改动时直接结束，**不给「无影响」结论**。

## 二、方法

1. **读上下文。** 读 `AGENTS.md`，以及 `docs/rules/工程配置.md`「项目规范」里与这次改动相关的规范；有工作项时读它的需求说明或 spec+plan。没有需求依据时照样分析代码，但不声称核过需求覆盖。工程配置里某一项还是占位或没写时，相关检查写成待验证项。只读和改动相关的部分。
2. **找行为变化。** 从差异定位改了哪些接口、类型、配置、数据结构、迁移、默认值、错误行为、副作用。新增代码也要看它在哪里注册、导出、写了什么状态，**不因「只是新增」就判低风险**。
3. **追调用方。** 在目标版本上**至少追一层直接调用方**，高风险的继续追间接调用方。每个调用方写明路径和行号、触发条件、影响哪个业务场景。
   - 文本搜索有盲区：Spring 依赖注入、事件监听、AOP、反射、MyBatis 映射文件、前端路由与动态组件。**找不到引用 ≠ 没有调用方**，这类地方列进覆盖边界。
   - 由外部调用的入口（命令行脚本、钩子、定时任务、部署脚本），调用方在配置文件和文档里：把这些配置和文档位置当作调用方列出。
   - 改动太大时，先列覆盖计划和优先级，没深入看的文件和调用链标为「未覆盖」，不写成低风险。
4. **查兼容性。** 按「三」逐类看，不相关的类别写一句「不涉及」和理由。
5. **分级。** 按「四」给每条影响标风险等级和证据确定性，合并重复项。

## 三、兼容性

先从仓库确认支持的环境，再判断有没有问题。**查不到支持范围时，写成待验证项，不臆造版本。** 需要核实某个 API 从哪个版本起可用时，查官方文档，不凭记忆。

| 类别 | 看什么 |
|---|---|
| 对外接口与错误码 | 参数、返回字段、序列化字段名、空值语义、默认值有没有变；错误码是否按工程的错误码规范（见工程配置「项目规范」）；已有调用方（前端、其他服务、QA 脚本）会不会受影响 |
| 配置与环境变量 | 新增必填项、改名、默认值变化，对照工程配置「部署」，看部署时要不要同步改 |
| 数据库迁移（Flyway） | 已执行的脚本不得修改；新旧版本并存时旧数据还能不能读；并行线之间撞号用 `python3 skills/team-check/team-check.py migrations --refs <集成分支> lane/<短名>` 查。这里只分析，不执行迁移 |
| 前端 | 浏览器范围先从 `package.json`、browserslist、Vite 配置确认；新语法靠转译、新 API 靠 polyfill，分开看；布局变化按 `docs/rules/UI设计规范.md` §4.1 的断点档逐档看 |
| 依赖版本 | JDK、Spring Boot、Node、前端框架大版本或其他依赖有没有提高环境门槛、去掉了什么能力 |

有意为之、已确认的破坏性变化，照样列出它影响哪些调用方，但不算缺陷。

## 四、分级

**风险等级**：
- **高**：有证据的接口契约破坏、核心行为回归、数据一致性问题，或在支持的环境里直接出错；
- **中**：有具体机制、但影响有限或还需验证的行为变化；
- **低**：有依据的局部影响。

**证据确定性**，与风险等级分开标：
- **已确认**：给出了代码位置，调用关系看得到；
- **推断**：根据命名、约定或间接线索推出来的；
- **待验证**：需要跑测试或查环境才能定。

已有的守卫、降级分支、转译和 polyfill 计入判断。不能只因为某个公共接口或新 API 有变化，就判定是缺陷。

## 五、报告

先在对话里给出主要发现（高风险项、需要重测的范围），再给报告。报告包含六部分：

1. **范围**：模式、基准 sha 和目标 sha（未提交模式写「工作区」）、读过的上下文、排除了哪些文件；
2. **改动概览**：涉及哪些模块、行为上变了什么；
3. **影响清单**：每条写改动位置、直接与间接调用方（路径和行号）、触发条件、业务影响、风险等级、证据确定性、待验证项；
4. **兼容性**：按「三」的五类逐一写结论；
5. **建议重测的范围**：要验证哪些行为、测试从哪一层打（参照本工作项 spec+plan 的测试落点）；
6. **覆盖边界**：没追到的调用链、文本搜索的盲区、仍不确定的结论，并写明「**静态分析，未运行测试**」。

## 六、落位

- **默认不存文件**：结论写进账本 note，一句话加最高风险等级，例如「diff-impact：`<基准sha8>..<目标sha8>`，高 1 / 中 2，波及订单导出接口」。
- **用来定复测范围时存档**：报告存为 `docs/tests/<版本>/影响分析-<工作项>.md`，带路径提交，账本 note 用 `commit:path` 引用。同名文件已存在时先读，再决定续写一节还是加后缀，不直接覆盖。

## 七、不是什么

- **不是评审结论**：不替代 `sa-review`、`technical-review`，不落评审状态；
- **不是测试证据**：不替代 `docs/rules/派活与交付.md`「四、证据」，报告里的「无影响」「低风险」都不能当作「测过了」；
- **不动手**：不改代码、不生成测试、不执行迁移。要修，另行派活。
