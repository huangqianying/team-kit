## 一、团队基建内核

本文、`docs/rules/团队协作契约.md`、`docs/rules/双端协作与交接.md`、`docs/rules/roles/`、两端入口 `.claude/` / `.codex/`、内核 skill 与 `.githooks/` 来自 **team-kit**，清单与来源提交记在仓库根 `.team-kit.json`。

## 二、班子与两类工作

**班子**：**SA 由当前值守会话（人 ↔ Claude Code 或 Codex）承担**；**PM / UI / SE / QA 为当前平台的 subagent**，均为资深。
共享角色正文见 `docs/rules/roles/`；Claude 入口在 `.claude/agents/`，Codex 入口在 `.codex/agents/` 并在 `.codex/config.toml` 注册。角色职责、标准链路与派活见 `docs/rules/团队协作契约.md`；两端配置、工具适配与换端交接见 `docs/rules/双端协作与交接.md`。

两端入口只保留共享角色的加载指令与各平台元数据、工具及模型配置；职责、流程、交付和落账要求统一维护在共享角色、契约与内核 skill 中。新增角色时同步添加两端入口及 Codex 注册，提交前核对引用的文件存在。

同一个班子做两类工作，**性质不同、纪律不同**，落账也分开计：

| | 产品开发 | 工程基建 |
|---|---|---|
| **产出** | 本产品本身——需求、设计、实现、测试、验收 | 让产品开发跑得更好的地基 |
| **谁做** | SA 派活，PM / UI / SE / QA 按标准链路分工 | 值守会话（SA）直接做，不派 subagent |
| **纪律** | **严格按契约走标准链路**：按契约 §二.1 分流（快速 / 增量 / 全链路）、评审只建议不阻断（§五）、结论落账本；subagent 在本次调用内交付结论并回报 SA | 不走产品链路；**但每项工作同样落状态账本，且结论必须附可复现核证**（命令 ＋ 输出），不凭印象宣称完成 |
| **落账** | 带产品版本号（取自 `system-version.json`） | 显式带 `--version _infra` |

**工程基建的工作范围**：

- **协作能力**：契约本身、状态账本 `skills/team-ledger/`、共享角色 `docs/rules/roles/` 与两端 subagent 入口
- **工程通用 skill**：`skills/*/SKILL.md` 的定义与演进（`.claude/skills` 与 `.codex/skills` 均软链至此）
- **交付与环境**：部署脚本与凭据、容器与反向代理、测试与生产环境
- **工程质量门禁**：git hooks、测试基线与套件约定
- **文档体系**：`docs/` 目录约定、洞见账本机制

基建工作项的**进展与结论落状态账本**（`--version _infra`），查看：`python3 skills/team-ledger/team-ledger.py stale --hours 0`。

**基建待办不落清单文件**，以产品负责人当面交代和账本为准。**账本被清空后不得假定待办还在** —— SA 须当场向产品负责人复述未完项并重新落账。

**两顶帽子分开戴**：值守会话既是 SA、又做基建，但两类工作不能混记——以 SA 身份做的设计裁定、技术终裁、合入动作属产品产出，须落账；基建改动不走产品链路，但同样要附可复现核证。**需求取舍仍归 PM 终裁；产品负责人的确认闸门（链路选择、UI 形态、迭代与版本验收放行、合入一句话）不可由 SA 代签。**

**subagent 不擅自改基建**：契约、账本工具、部署链、hook 有缺口时，按契约 §四「争议归口与升级」在结论与落账里写明 `契约缺口` ＋ 提请 SA，**不自行补规则往下跑**。

## 三、规范

### 3.1 项目文档管理规范

产品文档统一放在仓库根 `docs/` 下，根目录只保留入口和工具约定类文档。

> **本节只保留总入口，不展开目录结构。** 目录分类、版本产物命名与落位、评审记录与变更文档的
> 详细规则，一律以 **`manage-docs` skill** 为准。**两处都写会出现第二个事实源。**

- **SA 值守巡检以 `team-ledger` skill「SA 值守的每回合三步」为准**。**顺序是承重的** —— 先巡检，再派活。
- 需求 / 设计 / 测试 / 评审的归类、版本产物命名与落位，一律以 `manage-docs` skill 为准（**版本以子目录区分**）。
- 用户需求文档或需求变更正文由 PM 角色编写（角色职责见 `docs/rules/团队协作契约.md`）。
- **代码不入 docs**：代码工程放仓库对应目录（见工程配置「目录」），不放 `docs/` 下。

### 3.2 系统测试规范

产品测试分为**两级**，边界必须清晰、不互相替代、不互相复用，均由 agent 团队在标准链路内完成：

**① 研发自测试（SE）**

- 开发过程中编写并运行的**单元测试 ＋ 稳定集成测试**，随代码同仓、随实现一并提交；落位与命令见工程配置「目录」「命令」。
- 要求**快速、稳定、可频繁运行**；**核心逻辑单测覆盖率 ≥ 80%**。
- 目的：保证「实现正确、可频繁回归」，是代码开发步骤的组成部分，由开发方自负。

**② QA 独立测试（QA 独立验证）**

- QA 以**独立测试身份**接收开发交付物，依据测试方案 / 用例执行**系统测试**，对照验收标准**验收**，记录缺陷、产出测试报告。
- 目的：从独立视角保证「系统符合需求」；**不复用、不替代研发自测试**。**SE 自测通过 ≠ QA 测试通过**，产品负责人的合入确认以 QA 测试报告为依据。
- 可执行测试代码的落位见工程配置「目录」；测试方案、用例与报告的归类与落位见 `manage-docs` skill。

### 3.3 UI 设计规范

**文档：** `docs/rules/UI设计规范.md`（通用规则，内核）＋ `docs/rules/UI设计规范-本工程实例.md`（本产品的取值，按通用规则节号对应），二者合称「UI 设计规范」；通用规则的演示页 `docs/rules/ui-demo.html`（内核，浏览器直接打开）；主题文件位置见工程配置「项目规范」

前端 UI 的视觉与交互标准，与具体业务解耦，是新增或修改任何页面的**强制基准**；以令牌体系（色彩 / 排版 / 间距 / 圆角与材质 / 动效）统一管理，支持亮 / 暗双主题。

- UI 产出原型、PM 审查界面、SE 实现页面时，**均须以本规范为准**；变更规范前先更新文档：本产品的取值改本工程实例（PM 依据 PRD 维护）；通用规则在所有工程逐字相同，要改报 team-kit 维护方，不在工程里直接改。
- 本工程另有的项目规范（系统设计、错误码等）及各角色必读范围见工程配置「项目规范」。
- **写规则要有出处**：工程配置、本工程实例、项目规范里写进的硬约束，必须有出处——已有规约、产品负责人确认、现有测试或接口契约。只是「代码现在是这样」不能当成规则写进去；没有出处的写成「待确认」，并在账本挂一个工作项。已有条目不追溯，下次修改该条时补上出处。

### 3.4 协作与安全纪律

> 分支模型与发布方式见工程配置「分支与发布」；版本启动时 SA 按它确认分支策略（契约 §二 阶段 0），合入去向见契约 §五。

**多角色同 worktree 下的提交纪律**

每棵工作树都适用（主工作树与各并行线的工作树）。

- 提交前必须 `git status --porcelain`，**只 `git add` 自己产出的路径**。
- **禁止 `git add -A` / `git add .` / `git commit -a`** —— 同一棵工作树里常有别人未提交的改动，这三条命令会把它们一并带走。
- **提交一律带路径**：`git commit -m "…" -- <本次提交的全部路径>`。同一棵工作树里的各条线**共用一个暂存区**：不带路径的 `git commit` 会把别人已暂存、还没提交的改动一起提交走；带路径时只提交列出的路径，别人暂存的内容原样留在暂存区，提交钩子也只扫这些路径。
  - **新文件**先 `git add -- <新文件>` 再提交（没被 git 跟踪的路径不能直接写在 `commit` 后面）；**删除**直接把路径写进去即可；**改名**（`git mv`）新旧两个路径都要写，只写新路径时旧路径的删除会留在暂存区。
  - 提交后 `git show --stat HEAD` 核对：提交里只有自己的路径。
  - 暂存区里有不属于自己的内容时，**不替别人取消暂存**（不对别人的路径 `git reset` / `git restore --staged`），照常带路径提交自己的。
- 每个 commit 聚焦一个变更，保持 diff 小而聚焦；提交信息格式见工程配置「本工程补充规则」。

**覆盖类操作先读目标**

- `git checkout` / `restore` / `reset`、重定向覆盖、批量替换、删除与卸载：**执行前先看目标里是什么**并落账。
- **不回退用户或其他 agent 的未提交改动。**
- **不可逆且影响面超出本工作项的，先取得产品负责人确认。**
- 要回退文件时用备份 ＋ `cp` 回 ＋ 核 md5，不用 `git checkout <file>`；不用 `git stash`。
- **禁止 `--force` 覆盖他人分支。**

**工作树分工**

- 文档类工作（需求、原型、设计与规划、不属于任何线的文档）在**主工作树**内推进，按上面的提交纪律。
- 写代码的并行线各在**自己的工作树和分支**上推进，由 SA 合入集成分支，见 `docs/rules/并行线.md`。不开线时（工程配置没有「并行线」一节或没填，或日常开发分支就是 `main`），代码也在主工作树内推进。
- **评审 / 核证不需要另建 worktree** —— 各 worktree 共享同一对象库，一处 commit 全局立即可见。产物怎么读、怎么核证见契约 §三「取证口径」与 §五。

**密钥与钩子**

- 不提交真实密钥或机器相关路径；本地与部署凭据只放各自的不入库文件（见工程配置「部署」）。
- `.githooks/pre-commit` 拦截凭据文件与明文口令；**新克隆的仓库须先执行 `bash .githooks/install.sh`**，否则钩子不生效。
