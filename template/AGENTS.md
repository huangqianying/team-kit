## 一、项目概述

**产品名称：** 观澜（英文代号 **Vista**）· 全称：工作台账管理系统
**工程代号：** DeptTracker

> **命名分层策略**：对外 / 产品 / 界面 / 文档一律用「**观澜 Vista**」；仓库、目录、包名（`depttracker-prototype`）等**工程内部标识沿用 DeptTracker**，不做全局替换（避免破坏路径引用）。

面向组织 / 部门的台账管理系统，是本仓库要交付的最终产品。产品定位：**「人人工作台，向上汇聚成管理者视图」**——每个成员管理自己的全部工作，向上汇聚为管理者全局视图。其需求、设计、接口、测试、验收等全部产品文档统一放在仓库根 `docs/` 下。

## 二、班子与两类工作

**班子**：**SA 由当前值守会话（人 ↔ Claude Code 或 Codex）承担**；**PM / UI / SE / QA 为当前平台的 subagent**。
共享角色正文见 `docs/rules/roles/`（均为资深）；Claude 入口在 `.claude/agents/`，Codex 入口在 `.codex/agents/`。角色职责、标准链路与派活见 `docs/rules/团队协作契约.md`。

两端入口只保留共享角色的加载指令与各平台元数据、工具及模型配置；职责、流程、交付和落账要求统一维护在共享角色、契约与项目 skill 中。

同一个班子做两类工作，**性质不同、纪律不同**，落账也分开计：

| | 产品开发 | 工程基建 |
|---|---|---|
| **产出** | 观澜 Vista 产品本身——需求、设计、实现、测试、验收 | 让产品开发跑得更好的地基 |
| **谁做** | SA 派活，PM / UI / SE / QA 按标准链路分工 | 值守会话（SA）直接做，不派 subagent |
| **纪律** | **严格按契约走标准链路**：按 §二.1 分流（快速链路 / 全链路）、评审只建议不阻断（§五）、结论落账本、干完回报 SA | 不走产品链路；**但每项工作同样落状态账本，且结论必须附可复现核证**（命令 + 输出），不凭印象宣称完成 |
| **落账** | 带产品版本号（取自 `system-version.json`） | 显式带 `--version _infra` |

**工程基建的工作范围**：

- **协作能力**：契约本身、状态账本 `skills/team-ledger/`、共享角色 `docs/rules/roles/` 与双端 subagent 入口 `.claude/agents/` / `.codex/agents/`
- **工程通用 skill**：`skills/*/SKILL.md` 的定义与演进（`.claude/skills` 与 `.codex/skills` 均软链至此）
- **交付与环境**：部署脚本与凭据、容器与反向代理、测试与生产环境
- **工程质量门禁**：git hooks、测试基线与套件约定
- **文档体系**：`docs/` 目录约定、洞见账本机制

基建工作项的**进展与结论落状态账本**（`--version _infra`），查看：`python3 skills/team-ledger/team-ledger.py stale --hours 0`。

**基建待办不落清单文件**，以产品负责人当面交代和账本为准。**账本被清空后不得假定待办还在** —— SA 须当场向产品负责人复述未完项并重新落账。

**两顶帽子分开戴**：值守会话既是 SA、又做基建，但两类工作不能混记——以 SA 身份做的设计裁定、技术终裁、合入动作属产品产出，须落账；基建改动不走产品链路，但同样要附可复现核证。**需求取舍仍归 PM 终裁；产品负责人的确认闸门（UI 方向、验收放行、发版签字）不可由 SA 代签。**

**subagent 不擅自改基建**：契约、账本工具、部署链、hook 有缺口时，按契约 §四「争议归口与升级」在结论与落账里写明 `契约缺口` + 提请 SA，**不自行补规则往下跑**。

## 三、规范

### 3.1 项目文档管理规范

产品文档统一放在仓库根 `docs/` 下，根目录只保留入口和工具约定类文档。

> **本节只保留总入口，不展开目录结构。** 目录分类、版本产物命名与落位、评审记录与变更文档的
> 详细规则，一律以项目级 **`manage-docs` skill** 为准。**两处都写会出现第二个事实源。**

- **SA 值守巡检以 `team-ledger` skill「SA 值守的每回合两步」为准**。**顺序是承重的** —— 先巡检，再派活。
- 需求 / 设计 / 测试 / 评审的归类、版本产物命名与落位，一律以项目级 `manage-docs` skill 为准（详细目录结构与命名规则在该 skill；**版本以子目录区分**）。
- 用户需求文档或需求变更正文由 PM 角色编写（角色职责见 `docs/rules/团队协作契约.md`）。
- **代码不入 docs**：代码工程放仓库对应目录，不放 `docs/` 下（具体落位见 `manage-docs` skill）。

### 3.2 系统测试规范

产品测试分为**两级**，边界必须清晰、不互相替代、不互相复用，均由 agent 团队在标准链路内完成：

**① 研发自测试（研发方：BE / FE 自测）**

- 开发过程中编写并运行的**单元测试 + 稳定集成测试**，随代码同仓、随实现一并提交。
- 要求**快速、稳定、可频繁运行**；**核心逻辑单测覆盖率 ≥ 80%**。
- 目的：保证「实现正确、可频繁回归」，是代码开发步骤的组成部分，由开发方自负。

**② QA 独立测试（QA 独立验证）**

- QA 以**独立测试身份**接收开发交付物，依据测试设计方案 / 测试用例集执行**系统测试**，对照系统功能验收清单**验收**，记录缺陷、产出测试报告。
- 目的：从独立视角保证「系统符合需求」；**不复用、不替代研发自测试**，与研发自测试保持边界清晰。
- 测试产物（测试设计 / 用例 / 验收清单 / 测试报告）的归类与落位见 `manage-docs` skill。

### 3.3 UI 设计规范

**文档：** `docs/rules/UI设计规范.md`
**演示：** `docs/rules/ui-demo.html`（单文件零依赖，浏览器直接打开预览全部规范）

前端 UI 的完整视觉与交互标准，与具体业务解耦，是新增或修改任何页面的**强制基准**。设计目标：灵动 · 清晰（堪比 Apple 观感与手感），以令牌体系（色彩 / 排版 / 间距 / 圆角与材质 / 动效）统一管理，支持亮 / 暗双主题。

- PM 产出页面设计、SE 实现页面时，**均须以本规范为准**；变更规范前先更新该文档。
- 覆盖：设计令牌、三层材质工作台、多级菜单与 L3 页签、组织树（Master–Detail）、组织作查询条件、筛选栏、表格（固定表头 / 操作列收纳）、按钮、表单、弹窗、消息提示、无障碍等；末章附**新增页面检查清单**。

### 3.4 协作与安全纪律

> 分支模型与发布运行模式本规范不再写死：**分支策略由 SA 在版本启动时定**（契约 §二 阶段 0），合入去向见契约 §五。
> 本节只留与分支无关、但一旦不守就会出事的三条。

**多角色同 worktree 下的提交纪律**

- 提交前必须 `git status --porcelain`，**只 `git add` 自己产出的路径**。
- **禁止 `git add -A` / `git add .` / `git commit -a`** —— 同一棵工作树里常有别人未提交的改动，这三条命令会把它们一并带走。

**覆盖类操作先读目标**

- `git checkout` / `restore` / `reset`、重定向覆盖、批量替换、删除与卸载：**执行前先看目标里是什么**并落账。
- **不可逆且影响面超出本工作项的，先取得产品负责人确认。**
- 要回退文件时用备份 ＋ `cp` 回 ＋ 核 md5，不用 `git checkout <file>`；不用 `git stash`。
- **禁止 `--force` 覆盖他人分支。**

**同一工作树内协作**

- 一个工作单元跨 SE / SA / PM 等多角色时，各角色都在**同一棵工作树**内推进：产出者提交，产物 commit 落回同一分支。
- **评审 / 核证不需要另建 worktree** —— 各 worktree 共享同一对象库，一处 commit 全局立即可见。产物怎么读、怎么核证见契约 §三「取证口径」与 §五。
