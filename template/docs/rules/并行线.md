# 并行线

> 本文只定规范，不记变更由来。决策过程与历史在 git 与 `docs/insights/`。
>
> 本文规定多份工作同时推进时怎么判、怎么编排、写代码的线怎么隔离、怎么合入、怎么在测试服上验收。角色、链路与评审见 `docs/rules/团队协作契约.md`。
> 本工程的取值（最多并行线数、工作树位置、线内测试环境、测试服槽位）见工程配置「并行线」。
>
> - **集成分支**指工程配置「分支与发布」里的日常开发分支，它不是 `main`：线合入集成分支由 SA 做，进 `main` 才需要产品负责人一句话（七）。
> - **不开线**：工程配置里没有「并行线」一节或没填，或者日常开发分支就是 `main` 时，本工程不开线，按契约 §三「不开线时」执行。
> - **不追溯**：本文生效前已开工的版本、迭代和工作项按原安排推进，不补并行编排、不改用线；新开的才适用。

## 一、何时判并行

| 场景 | 何时判 | 写在哪 |
|---|---|---|
| 全链路 | 阶段 2「系统设计与迭代规划」 | 迭代规划的「**并行编排**」一节（必填，见二） |
| 增量链路 | 同一时段有两个以上增量工作项要开工：SA 判级之后、派活之前 | 工作项 `并行编排-<日期>`：一条账本 note，必要时另写一页（简版，见二末） |
| 迭代或工作项内部 | 一份 spec+plan 的 task 可分给多个 SE，或用例可分给多个 QA | 契约 §三「同角色并行」 |

- **默认并行。** 依赖关系允许就按并行编排。选串行要落一条账本 note，写明是哪一项依赖或哪一项资源不允许。
- **判据**：
  - 一方是否需要另一方**还没冻结**的接口或数据结构；
  - 是否改同一批文件、同一张表；
  - 资源（测试环境、机器负载）能否隔离。
- **接口冻结后即可并行。** 依赖只在接口上的，接口冻结之后就并行，不必等上游验收。
- **快速链路的工作项默认不开线**，留在主工作树带路径提交。只有它和某条线改到同一批路径时，才排在那条线之后，或者并进那条线。
- **不在线上的工作项**：快速项，以及编排里没有单独开线的写代码工作项（例如同一时段只有它一项），留在主工作树、直接提交到集成分支。它们照常部署测试服验收（六），同样要有验收通过的结论才能进 `main`（七）。

## 二、并行编排

迭代规划里的「并行编排」写六项：

1. **依赖图**：每个迭代依赖谁，依赖的是什么（接口、表、数据、判据）。
2. **线的划分**：
   - 每条线承载哪个或哪几个迭代；
   - 线的短名：ASCII，用作分支名和目录名；
   - 开工条件：「某接口已在某提交冻结」或「某线已合入」。
3. **接口冻结点**：下游线开工前，上游须先提交并冻结的接口（类型、接口契约、表结构），以提交号为准。冻结后要改，报 SA，由 SA 通知所有受影响的线。
4. **归属**：
   - 每条线能改哪些路径；
   - 共享文件（公共框架包、`.gitignore`、根配置、依赖清单）归谁改，其他线要改时报 SA；
   - 每条线有几个迁移脚本，只写数量，编号在合入时定（见五）。
5. **合入顺序**：预定的合入顺序，也就是测试服的验收顺序。可以按实际进度调整，调整时落账。
6. **并行线数**：同时活跃的写代码线不超过「最多并行线数」。默认 **3**，工程配置可另设。

**增量链路简版**写四项：哪几项并行、各自能改哪些路径、共享文件归谁、合入顺序。

## 三、线的创建与收尾

**一条线 = 一个工作树 + 一个分支**，承载一个迭代或一个增量工作项的全部代码类产出。

**创建**：由 SA 在派出第一棒之前完成。

- **分支**：`lane/<短名>`，从开工条件对应的提交拉出。
- **工作树**：放在工程配置「并行线」指定的位置，默认 `../<工程目录名>.lanes/<短名>`。**不得放在工程目录内**，否则工程的测试、lint、搜索和钩子扫描会扫进嵌套的工作树。
- **初始化**：新工作树里没有被 git 忽略的本地文件（依赖目录、本地凭据、`.env` 等），按工程配置「并行线」的「工作树初始化」准备。
- **落账**：在该工作项 note 里写短名、分支、工作树路径、起点提交。

**提交去向**：

| 产出 | 提交到 |
|---|---|
| 该线的 spec+plan、代码、研发自测试、QA 的测试方案+用例、可执行用例、测试报告、QA 证据 | 线分支，在线的工作树里提交 |
| 版本级文档（需求文档、UI 原型、系统设计与迭代规划），以及不属于任何线的文档类工作 | 集成分支，在主工作树里带路径提交 |

- 评审与取证照旧用 `commit:path` 指认。各工作树共用一个对象库，线分支上的提交随时可读。
- **谁进线的工作树**：
  - 进：该线的 SE（可以多个，属于线内的同角色并行）、给该线做测试的 QA；
  - 不进：PM 做界面审查、SA 评审时只读，按提交读。
- **线内流程不变**：spec+plan → SA 评一次 → 扇出 QA → 编码与研发自测 → QA 独立测试 → 测试报告。
- **不改写历史**：线分支上不 `rebase`、不 `squash`、不 `push --force`。账本和评审里的 `commit:path` 必须一直可读。需要上游改动时，在线里 `git merge <集成分支>`。

**收尾**：线合入集成分支、集成自测通过之后（五.5）：

1. 用 `git -C <线的工作树> status --short --ignored` 核工作树里的全部产出。**被 git 忽略的文件（如测试输出目录），`git worktree remove` 会直接删掉、无法恢复**，`git status` 不带 `--ignored` 看不到它们。证据须已提交，或已按 QA 规则另存到工作树之外；
2. 再 `git worktree remove <线的工作树>` 和 `git branch -d lane/<短名>`。

删除前先看目标里有什么，见 `AGENTS.md`「覆盖类操作先读目标」。

## 四、线内测试

- QA 的系统测试在**该线自己的隔离环境**里跑，不占测试服的验收部署。
- 隔离做法见工程配置「并行线」的「线内测试环境」：端口、数据库、compose 项目名、临时目录、浏览器 profile 各线分开。可以在本机，也可以在测试服上加前缀并排部署。
- 测试报告写明**被测提交**，也就是线分支上的提交号。

## 五、合入集成分支

由 SA 按并行编排的合入顺序合入。前提是该线的 QA 测试报告已提交。

- **报告里有 `阻断` 时**：先在线内修复、重测受影响部分，再合入，不让它拖累其他线。产品负责人可特批带着 `阻断` 合入（落账写明）。合入 `main` 的裁定权仍归产品负责人（契约 §五）。

**前提**：主工作树检出集成分支；git ≥ 2.38（`merge-tree --write-tree` 需要）。**一次只合一条线**，上一条落账后再开始下一条。

合入步骤：

1. **迁移定号**（本线有迁移脚本时）：线内迁移脚本用占位编号。在**上一条线合入之后、紧挨本线合入之前**，由线的 SE 改成集成分支上的下一个空号，在线分支上提交。不得让两条线同时定号。线内隔离库是一次性的，改名不违反「已执行脚本不得修改」。**合入后编号不得再改。** 合入前可以用 `python3 skills/team-check/team-check.py migrations` 核对迁移版本号没有重复。
2. **预检冲突，不动工作树**：`git merge-tree --write-tree <集成分支> lane/<短名>`。
   - 退出码 0：无冲突，第一行输出是合并后的树；
   - 退出码 1：有冲突（输出含 `CONFLICT`）。退回该线，由线的 SE 在线的工作树里 `git merge <集成分支>`、解决冲突、跑研发自测、提交后再报 SA；
   - 线分支上有了新提交（定号、解冲突），都要**重新预检**，以最后要合的那个提交为准；
   - **SA 不在主工作树里解冲突。** 主工作树停在冲突合并状态时，其他人的带路径提交会全部失败（`cannot do a partial commit during a merge`）。
3. **核迁移版本号**（本线有迁移脚本时）：`git ls-tree -r --name-only <预检输出的树> -- <迁移目录>`，确认合并后迁移脚本的版本号没有重复。文件名不同的两个同号脚本不会产生 git 冲突，只能这样查。
4. **合入**：在主工作树执行 `git merge --no-ff lane/<短名>`。下面两种情况 git 会拒绝合入，主工作树保持原样，稍后重试，**不替别人取消暂存、不动别人的改动**：
   - 暂存区里有别人已暂存、未提交的内容（不论是否相关，整体拒绝）；
   - 别人未暂存的改动碰到了本次合入涉及的文件。
5. **集成自测**：合并提交上没有人整体测过。由刚合入那条线的 SE 在合并提交上跑「构建 + 研发自测全量」，全绿后才能部署验收（旧失败按 `docs/rules/派活与交付.md`「五」单列，不影响全绿）。
   - 做法：线的工作树 `git checkout --detach <合并提交>`，或另开临时工作树（同样放在工程目录之外）。
   - 失败就在集成分支上修，见六。
6. **落账**：合并提交号、合入了哪条线、迁移编号、集成自测结论。

## 六、测试服与验收

- **一个槽位同一时间只放一个部署**，部署对象一律是集成分支上的提交，不部署线分支。槽位数默认 **1**，工程配置可另设。
- **排队顺序 = 合入顺序**。一条线合入且集成自测通过后（不在线上的工作项则在其测试报告提交后），SA 部署当时的集成分支头，通知产品负责人验收。
- **前一个验收还没结束时**，新部署要不要覆盖由 SA 判：
  - 部署是累加的，正在验收的迭代的改动仍在新部署里；
  - 那次验收换一个提交接着做，结论注明基于哪个提交；
  - 负责人正在操作时不覆盖。
- **一次部署可以出多份结论**：
  - 每个迭代的验收结论单独落账：PM 需求符合性 note ＋ 产品负责人一句话，各自注明基于哪个部署提交；
  - 验收时带着先合入的其他迭代的改动，这是允许的。
- **验收不通过**：
  - 在集成分支上修，不回退；
  - 由原线的 SE 开一条修复线 `lane/<短名>-fix<N>`，按五合入；
  - 是否只跑受影响的测试、QA 是否复测，由 SA 按改动范围定；
  - 修好后重新部署，受影响的验收项重做。
- **测试服占用记在账本**，工作项名 `测试服验收`（槽位数大于 1 时为 `测试服验收-<槽位>`）。任何时候都能从账本读出测试服上是哪个提交、在等谁。
  - 部署时落 `进行中`，note 写「部署 `<提交>`，包含 `<线…>`，供 `<迭代…>` 验收」；
  - 等负责人验收时落 `阻塞 --blocker-role owner`，进入待裁决清单；
  - 没有待验收的内容时落 `完成`。

## 七、进 main

- **两类合入归属不同**：
  - 线合入集成分支是 SA 的集成动作，不需要产品负责人那一句话；
  - 产品负责人的「合入一句话」管的是集成分支合入 `main`（契约 §五）。
- **集成分支整体进 `main` 的前提**：自上次进 `main` 以来，进入集成分支的每个工作项（线、快速项、不在线上的工作项）都已有**验收通过**的结论。有任一项未验收，或验收不通过还在修，就先不进。
- **验收结论是什么**：
  - 快速项的验收结论 = 快速链路第 4 步产品负责人的一句话确认；
  - 增量项、迭代的验收结论 = PM 需求符合性 note ＋ 产品负责人一句话（六）。
- SA 请负责人一句话时，列出这次会带进 `main` 的各项及各自的验收结论。
- **想让先通过的项早进 `main`**：在并行编排里把它排在前面、让后面的线晚些合入，**不从集成分支里单独挑出来**，单独挑会改写历史。
- **全链路**：版本内各迭代本来就在系统验收之后才进 `main`。

## 八、SA 的职责

- **有线在跑时，SA 不写产品代码**，只做派活、评审、合入、部署、落账，精力留给交汇点。
  - 合入冲突退回线内（五）；
  - 集成自测与验收修复交线的 SE；
  - 基建工作不受此限（`AGENTS.md`「两顶帽子分开戴」）。
- **每回合巡检第 3 步**（`team-ledger` skill「SA 值守的每回合三步」）：对照进行中版本的并行编排，找出三类项，逐条派出、合入或补理由（可以用 `team-check.py plan <迭代规划>` 核编排是否齐全，`team-check.py lanes` 核工作树与登记的线）：
  - 已满足开工条件却还没派出的线；
  - 已有 QA 报告却还没合入的线；
  - 没写理由就串行的项。
- **开线不超过最多并行线数**：默认 3，工程配置可另设。
- **恢复会话时**，`git worktree list` 与账本里登记的线逐条对上。不认账本以外的工作树，例如工具自建的。
