# 派活与交付

> 本文只定规范，不记变更由来。决策过程与历史在 git 与 `docs/insights/`。
>
> 本文规定几个角色共用的格式：SA 派活时写什么，角色回报时写什么，spec+plan 必须写明什么，证据怎么记，旧失败怎么处理。角色、链路与评审见 `docs/rules/团队协作契约.md`。
> **只规定必须包含的内容，不规定文档骨架**：章节怎么排、编号怎么写由各工程自定。
> **不追溯**：本文生效前已开工的工作项按原安排推进，已有文档不改写；新开的工作项适用。

## 一、派活单

SA 派活时写明下列字段：

| 字段 | 写什么 |
|---|---|
| **目标与预期产物** | 做什么；交付哪些产物，写到路径级别 |
| **工作依据** | 工作树、产物位置及依据版本（`commit:path`）。版本须真实可定位，位置可以用路径、章节、符号或行号，行号须对应所引版本（取证口径见契约 §三）。**开发类派活另写起点提交**（见下） |
| **工作项** | 原 ledger item 名，同一工作项沿用原名；同一工作项内并行的子产物写 `--part` |
| **可写范围** | 本次可以改动的路径或目录 |
| **禁写范围** | 明确不能碰的路径：共享文件、别的线或别的实例负责的路径 |
| **验证方式** | 交付前要跑的命令或判据 |
| **依赖** | 要等哪个提交或产物；没有写「无」 |
| **资源** | 端口、数据库、工作树等隔离参数 |

- **快速链路只填 4 项**：目标与预期产物、工作依据、工作项、验证方式。但快速项并进并行线，或者同角色并行时，可写范围、禁写范围、资源也要填。
- **增量链路、全链路全部字段都写**，不适用的写「无」。同角色并行或并行线时，资源必填（`docs/rules/并行线.md`）。
- 可读范围不单列：读什么、以哪个版本为准，按契约 §三「取证口径」。
- 可以附必要背景和已批准的约束；独立评审不预设结论。
- **起点提交**：本工作项**首次开发派活**时，SE 开工所基于的集成分支提交；并行线的工作就是线的起点。
  - 之后的返工、修 QA 报出的问题、QA 测试、合入后的集成自测，都沿用这一个起点提交，不随每次派活变化；
  - 它用于「四」的先失败再通过和「五」的旧失败分类。
- **派活落账时**：开发派活写 `--phase dev`，首次用 `--base <起点提交>` 记下起点（账本会核对它存在，并在 `stale` 里显示）；填了可写、禁写范围的，在 note 里写一行。派活消息本身不落盘，换端接班后要靠这一行核对。

## 二、回报

角色在本次调用结束时回报四项，顺序固定：

1. **状态**：`完成` / `阻塞` / `失败`。
   - `失败`：尝试了但没做成，比如本次改动引起的测试失败、命令出错；
   - `阻塞`：缺输入，或在等别人；
   - 按「五」单列的旧失败、不稳定项，不影响状态，照常写 `完成`；
   - 没有产物提交的回报（只读排查、运维、咨询），落账用 `--no-commit '理由'` 写明；
   - 落账时，`失败` 和 `阻塞` 都记为 `阻塞`：`--blocker` 写明原因；`--blocker-role` 写接续方，由谁接着处理就写谁，拿不准写 `--blocker-role sa`，由 SA 决定重派或转交。
2. **实际改动**：本次派活产生的**全部提交**的提交号，以及各提交改动的路径（逐个 `git show --stat <提交>`）。没有提交就写「无提交」，并说明原因。
3. **验证**：实际运行的命令、退出码、运行时间、被测提交。评审类工作写明评审了哪个 `commit:path`。
4. **未完成与下一步**：没做完的部分；需要别的角色接手时写「需 X 角色做 Y」。角色不自行派活。

**SA 收到回报后核对**：派活单写了可写范围的，核对实际改动的路径全部落在可写范围内、没碰禁写范围。没填可写范围的（快速链路默认如此），不做越界核对。
- **越界的部分不算本次交付**：SA 落账写明越界路径，交给这些路径的负责方核对。
- **不自动回退**：要回退时，按 `AGENTS.md`「覆盖类操作先读目标」执行；影响超出本工作项的，先经产品负责人确认。

## 三、spec+plan 必须写明

适用于增量链路和全链路。快速链路不写 spec+plan。

- **测试落点**：每类 AC 的测试打在哪个公共接口上（例如对外 HTTP 接口、页面、服务门面），以及理由。
  - SA 评审 spec+plan 时一并核这一项。它和其他评审意见一样是建议级：SE 可以不采纳，在账本 note 写明理由；有分歧时按契约 §四 由 SA 技术终裁。
  - QA 的独立测试原则上也打在同一层，或比它更外的一层。
- **每个任务写明两个字段**：
  - **覆盖**：本任务覆盖哪几条 AC，或 US / NFR 编号；
  - **依赖**：要等哪些任务完成；没有写「无」。

  写成表格的一列或每节一行都可以。spec+plan 写出后，SA 用这两个字段核对它与并行编排（`docs/rules/并行线.md`「二」）一致，需求覆盖度对账（契约 §五）也以它们为准。

## 四、证据

SE 的研发自测和 QA 的测试报告都要包含下面三块。章节名和编号由工程自定。

1. **AC 追溯**：每条 AC 一行，写明四项：
   - AC 编号；
   - 结果：通过 / 不通过 / 未核 / 延期 / 豁免；
   - 执行内容：用例或测试名；
   - 证据位置。

   SE 的研发自测按任务列出覆盖的 AC。快速链路没有 AC 编号时，按需求说明或复现指针的要点逐条追溯。
2. **运行记录**：每次全量或关卡运行写明被测提交、命令、退出码、时间。**不写这几项的「全部通过」不算证据。**
3. **先失败再通过**（只要求 SE）：
   - **每条 AC 至少一条**：选守护它的主要测试，记测试名、在起点提交上的失败摘要、在交付提交上的通过摘要；
   - **保持类 AC**（不变、不回归、兼容）在起点提交上本来就通过，写「不适用：起点即通过」，并给出守护测试名；
   - **修 BUG 时的回归测试，每个都记一条**，快速链路也一样；
   - **不规定先写测试还是先写实现**：实现之后再把新测试放到起点提交上跑一遍、取它的失败输出，同样算数。

**证据落在哪**：
- **增量链路、全链路**：SE 的研发自测记录写进本轮 spec+plan 文档里单独的一节，随文档提交；QA 照旧写测试报告（落位见 `skills/manage-docs/SKILL.md`）。
- **快速链路**：写进回报和账本 note：运行记录，以及修 BUG 时回归测试的先失败再通过。

## 五、旧失败

**分类**：运行测试时出现失败，先在**起点提交**（见「一」）上重跑这一项，最多 3 次：

| 起点提交上的结果 | 归类 | 处理 |
|---|---|---|
| 每次都失败 | **旧失败** | 见下 |
| 每次都通过 | **本次回归** | 必须修复。交付提交上时好时坏的，可能是本次引入的竞态，同样算本次回归 |
| 结果不一致 | **不稳定** | 按旧失败处理，单独标明。**只有起点提交上本身就时好时坏，才算不稳定** |

**已知旧失败清单**：每个工程一份，位置 `docs/tests/已知旧失败.md`。
- 每条写测试名、首次发现的提交、失败摘要、产品负责人确认的日期。
- **只有产品负责人确认过的才能进清单。**
- 清单由 QA 维护：负责人裁定豁免后，SA 派 QA 在**主工作树**上把它写进清单，提交到集成分支（带路径提交）；清单在第一次需要写入时创建。工程里还没有这份清单时，视为空清单。
- 工程原先记在别处的已知失败（例如账本里的工作项），由 QA 整理，经负责人确认后迁入。

**处理**：
- **清单内的失败**：报告里引用清单条目即可，不再请负责人确认。
- **清单外的旧失败或不稳定项**：
  - 保留原始失败输出，在回报和报告里单独列出，**不计入通过，也不悄悄跳过**；
  - 工作照常推进，不停下等负责人；
  - SA 在请产品负责人做验收或合入的那一句话时，列出这些新发现，由负责人一并裁定：豁免并进清单，或者要求修复。
- **不影响「全绿」**：契约和 `docs/rules/并行线.md` 里「研发自测试全绿」「全绿后才能部署验收」的「全绿」，指的是除清单内旧失败和按本节单列的项以外全部通过。
  - 回报状态照常写 `完成`，这些项在「验证」里单列；
  - QA 把它们单列为旧失败，不标 `阻断`，不进发现分级。
- **修复旧失败另立工作项**，修好后从清单里删掉这一条。
