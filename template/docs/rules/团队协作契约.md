# 团队协作契约

> 本文只定规范，不记变更由来。决策过程与历史在 git 与 `docs/insights/`。
>
> **SA 由当前值守会话（人 ↔ Claude Code 或 Codex）承担；PM / UI / SE / QA 是当前平台的 subagent**。
> 共享角色正文在 `docs/rules/roles/`；原生入口分别在 `.claude/agents/` 与 `.codex/agents/`。你若是 subagent，动手前先读对应共享角色，确认自己的职责。
> 调度工具名称与参数依当前平台运行时，工具及模型配置留在对应平台入口；两端共用本文的派活、交付与落账要求，两端配置与换端交接见 `docs/rules/双端协作与交接.md`。项目工具用法见各 skill，本文不复述。
> 本工程的产品、目录、命令与分支策略见 `docs/rules/工程配置.md`。
> 多份工作同时推进时的编排、写代码的线（各自的工作树与分支）、合入集成分支与测试服验收见 `docs/rules/并行线.md`。

## 一、角色

**五个角色，均为资深。全链路中每份产物都有非本人的对手方评审（建议级，见 §五），无人自产自评；增量链路中 SE 的 spec+plan 由 SA 评、实现由 QA 独立测试；快速链路中 QA 的独立测试即对手方。**

| 角色 | 职责 | 产出 | 评谁 |
|---|---|---|---|
| **PM** 资深产品经理 | 需求最高权威：写需求文档、验收需求符合性；**交互与视觉**：维护 UI 规范、**定界面上「什么必须成立」（立进需求文档作 AC）**、原型审查、前端界面审查 | 需求文档、需求符合性结论、原型审查结论 | SA 产物的**需求符合性**；**UI 的原型**（需求符合性 ＋ 规范符合性）；SE 实现的界面 |
| **UI** 资深 UI 原型工程师 | **只做 Web UI 原型** —— 版本需求设计及迭代内按需补充的形态，依据恰两份（SA 指定版本的需求文档 ＋ `docs/rules/UI设计规范.md`）。**要保住的是「快速修改 · 快速看效果 · 快速确认」** | `prototypes/<版本>/` 下的 Web UI 原型（**一次性产物，不长成产品前端**） | **不评谁**（纯产出方；由 PM 审、产品负责人确认形态） |
| **SA** 资深系统架构师 | 系统框架与边界、**技术选型与标准、攻关、编写和维护迭代规划**、调度、合入；**需求上服从 PM** | 系统设计（含技术选型与方案）、迭代规划、技术评审意见 | PM / SE / QA 的产物（建议级）；原型的技术可行性争议 |
| **SE** 资深开发工程师 | 写 spec+plan、编码、修 bug（含自测）；**含产品前端 —— 它与原型是两份产物，在 `prototypes/` 之外另写（目录见工程配置「目录」）** | spec+plan、代码（后端 ＋ 产品前端）、可实现性结论 | SA 产物的**可实现性** |
| **QA** 资深测试工程师 | 测试方案、用例、执行测试、报 bug、出报告 | 测试方案、用例、测试报告 | 以独立测试身份验证 SE 的实现 |

**两条权轴**：PM 管「做什么」（需求 ＋ 体验）；SA 管「怎么做 ＋ 执行」。SA 是产品负责人的日常对接人；PM 只在需求定义期直接对接。**UI 原型是形态的事实源与前端开发的强制依据**；原型代码是一次性产物，不长成产品前端；不写文字版界面设计稿。

## 二、标准链路

> 每阶段依次执行；`→` 后为下一步，括号内为执行 / 评审角色。**评审不阻断**（§五）；**合入由产品负责人一句话决定**。工作项先按入口分流（§二.1），再走对应链路。

### 2.1 工作项入口：三种情况

| 入口 | 处理 | 链路 |
|---|---|---|
| **① 开发新版本** | 按迭代增量方式开发，**一律走全链路** | §二.4 全链路 |
| **② 当前版本内新增功能** | SA 判功能复杂度（判据见下），**产品负责人确认走哪条链路后才开工**；产品负责人可改判 | 简单 → §二.2 快速链路；复杂 → §二.3 增量链路 |
| **③ 当前版本内修复 BUG** | SA 判 BUG 复杂度，**产品负责人确认走哪条链路后才开工**；产品负责人可改判 | 简单 → §二.2 快速链路；复杂 → §二.3 增量链路（PM 在第 1 步为该 BUG 立需求说明） |

**复杂度判据**只看编码规模与影响面，不看风险：**简单** = 同时满足 ① 不新增页面 ② 不动数据库迁移 ③ 不动权限模型；任一不满足即**复杂**。BUG 的「复杂」另含：根因在需求或设计层（修法需改需求 / 改设计）。

版本内的复杂项默认走增量链路；规模接近一个版本（如新增独立功能模块）时，产品负责人可改判为全链路。

### 2.2 快速链路（4 棒）

| 步 | 角色 | 产出 |
|---|---|---|
| 1 需求 | PM | 需求说明：一段话落账本 note（必要时 `docs/prds/` 一节），**不出 PRD 全文、不出 UI 原型**；BUG 由 SA 直接给 SE 复现指针，**跳过本步** |
| 2 开发 | SE | 代码 + **研发自测试全绿**；改到界面按 `docs/rules/UI设计规范.md` 自查 |
| 3 测试 | QA | 系统测试 + 测试报告（发现分级，见 §五） |
| 4 合入 | 产品负责人 | **一句话确认** → SA 按分支策略合入、推送、落账；集成分支进 `main` 按 `并行线.md`「七、进 main」 |

SA 在快速链路里**不出设计、不评审、不复跑**，只派活、落账、合入。

### 2.3 增量链路（当前版本内的复杂需求 / 复杂 BUG，5 棒）

| 步 | 角色 | 产出 |
|---|---|---|
| 1 需求 | PM（+ UI 按需） | **需求说明一份**（落 `docs/prds/<版本>/`）：范围与不做、各角色所见、验收标准（AC）；复杂 BUG 写清现象、根因所在层级与修复后的应有行为。**涉及新页面或新交互形态时**加 UI 原型（UI，落 `prototypes/<版本>/`）→ 产品负责人确认形态；只删减或在既有页面上小改时不出原型 |
| 2 方案 | SE → SA | **spec + plan 一份文档**（SE）：数据 / 接口 / 权限 / 迁移设计、需求覆盖度对账、task 拆分 → SA 评一次（建议级）→ **扇出 QA**（规则同 §二.4，一次且仅一次） |
| 3 开发 | SE（+ PM） | 代码 + **研发自测试全绿**；改到界面时 PM 界面审查一轮（建议级） |
| 4 测试 | QA | 可执行用例 + 系统测试 + 测试报告；AC 追溯写进报告，**不单出测试方案文档、不送 SA 评审** |
| 5 合入 | 产品负责人 | PM 需求符合性结论（账本一条 note）→ **产品负责人一句话确认** → SA 按分支策略合入、推送、落账；集成分支进 `main` 按 `并行线.md`「七、进 main」 |

SA 在增量链路里**不出系统设计**，负责判级、评 SE 的 spec + plan 一次、派活、落账、合入；技术终裁权不变（§四）。与全链路相比不做：版本启动与归档、SA 系统设计文档、需求 + 设计合评、测试方案单独成文与评审；UI 原型按需。

**多项同时进行**：同一时段有两个以上增量工作项要开工时，SA 先按 `并行线.md`「二、并行编排」写简版，再派活；能并行的各开一条线，各自走完本链路的 5 步。

### 2.4 全链路

**版本启动 → 需求设计 → 系统设计与迭代规划 → 逐迭代执行「开发 → 测试 → 验收」→ 全部迭代完成后系统验收。** 前三阶段建立版本基线；迭代按规划交付可运行的增量，系统验收覆盖整个版本。

| 阶段 | 执行角色 | 步骤 | 下一棒 |
|---|---|---|---|
| **0 版本启动** | SA | 产品负责人告知启版 → 核对上一版收尾状态 → 确定新版本号、版本产物目录与分支策略，更新版本状态并落账。**只建版本容器，不代 PM 定需求** | → PM |
| **1 需求设计** | PM / UI | 版本需求文档(PM) → **UI Web 原型(UI，落 `prototypes/<版本>/`)** → 原型审查(PM，一轮：需求符合性 + 规范符合性) → **产品负责人确认形态**；原型技术可行性有争议时交 SA 裁定 | → SA |
| **2 系统设计与迭代规划** | SA | 系统设计（含技术选型与方案）＋ **迭代规划**（范围、顺序、依赖、每轮可运行的交付与验收路径、US / NFR 落点，以及必填的「**并行编排**」，见 `并行线.md`「二」）→ **需求 + 设计 + 规划合评一次**（SE 判可实现性、PM 判需求符合性，建议级）；规划落 `docs/designs/<版本>/` | → 第一个迭代 |
| **3 迭代开发** | PM / UI / SE / QA / 产品负责人，SA 调度 | **按并行编排推进**：可并行的迭代各开一条线（`并行线.md`），每个迭代执行下表的开发、测试、验收，**各自验收**；每轮验收结论及接续安排落账 | → 后续迭代按编排开工；全部完成后 → 阶段 4 |
| **4 系统验收** | QA / PM / 产品负责人，SA 收口 | QA 汇总各迭代报告及跨迭代验收证据，补验版本剩余的集成路径与未核项；PM 给版本级需求符合性结论（账本 note），逐项说明延期和未核差集 → **产品负责人明确版本验收放行** → SA 按分支策略合入、推送、记录版本结束与归档 | 终点 |

**阶段 3：每个迭代的开发、测试、验收**

| 步骤 | 执行角色 | 产出与交接 |
|---|---|---|
| **3.1 迭代开发** | PM / UI 按需，SE 开发，SA 调度 | PM 承接本轮需求范围与 AC；已有版本需求可直接引用，需细化或变更时补迭代需求说明。新增页面或交互形态时，由 UI 补原型 → PM 审一轮 → 产品负责人确认新增形态，已确认且未变的形态沿用。SE 编写本轮 **spec + plan 一份文档** → SA 评一次（建议级）→ **扇出 QA 准备测试** → SE 编码、研发自测试；界面有改动时 PM 产品界面审查一轮（建议级）→ 交 QA |
| **3.2 迭代测试** | QA | 本轮 **测试方案 + 用例一份文档** → SA 评一次（建议级）→ 独立系统测试与必要回归 → **迭代测试报告**（含 AC 追溯、发现分级、延期及未核项）→ 交 SA 安排本轮验收 |
| **3.3 迭代验收** | PM / 产品负责人，SA 收口 | PM 给本轮需求符合性结论（账本 note）→ **产品负责人确认本轮验收及下一步** → SA 按版本分支策略处理交付、部署 / 推送与落账；继续下一轮时承接剩余项，最后一轮结束后进入系统验收。验收部署的是集成分支上的提交，按合入顺序排队、累加部署；验收不通过在集成分支上修，不回退（`并行线.md`「六」） |

迭代规划由 SA 随范围与依赖变化维护，需求取舍仍归 PM 和产品负责人；延期、未核和跨迭代验收项须有明确去向。**迭代验收只覆盖本轮，版本级系统验收在全部迭代完成后单独收口。** 产品负责人要求继续下一轮、部署或推送时，按其明确指示推进，不能据此把未核项记成通过，或代签版本验收。系统验收承接已有有效证据，按剩余差集补验，不机械重跑所有已通过的测试；结论仍按 §五处理。

**每个迭代的扇出点 —— 本轮 spec+plan 评完后**：**由 SA 派 QA 起本轮测试准备线，一次且仅一次**，SE 同时推进编码。SE 在结论里写明「测试线可起」；SA 负责实际派出及后续唤醒，续派沿用本轮工作项，不重复开线。QA 可先完成方案、用例和工具准备，实际系统测试等待 SE 交付明确版本的可运行产物。两线汇合于 QA；方案用例未写完先写完，已就绪则接收 SE 交付。§二.3 的扇出同此规则。

## 三、派活

**SA 统一派活，账本只记录状态。** PM / UI / SE / QA 需要其他角色出手时回报 SA，不自行派活。

**两端运行纪律**：同一时刻只有一个值守会话推进同一工作项。Claude Code 与 Codex 使用同一角色职责、版本、工作树和账本；切换工具不重开需求、不重置状态、不重复扇出 QA。异步工具返回任务 ID 只表示已派出，SA 须等到实际交付结论；恢复会话时先核活动任务，不能把账本里的「进行中」当作仍有活跃 agent。旧宿主的任务 ID 不能在新宿主续用，接力用原 item ＋ 已提交产物 ＋ 工作树状态重新派活。换端步骤见 `docs/rules/双端协作与交接.md`。

派活说明：

- **目标与范围**：做什么、交付什么。
- **工作依据**：工作树、产物位置及依据版本；版本须真实可定位，位置可用路径、章节、符号或行号，行号须对应所引版本。
- **原 ledger item 名**：同一工作项沿用原名。

可附必要背景和已批准的约束；独立评审不预设结论。

### 同角色并行

- 是否起同一角色的多个 subagent、起几个、怎么分，**由 SA 决定**；各角色不自行另起同角色实例。
- 起之前须同时满足：
  - 各份工作互不依赖，或者依赖的接口已冻结；
  - 改动路径不重叠；
  - 端口、工作目录、数据库、浏览器等资源各自隔离；
  - **写代码的线各用自己的工作树和分支**（`并行线.md`「三」）。

  不满足的部分串行，其余仍然并行。**能并行就并行**，选串行要在账本里写理由（`并行线.md`「一」）。
- 派活说明另写：本实例负责哪一份、能改哪些路径、用哪些资源、由谁汇总。
- 一个工作项只出一份结论：由 SA 指定一个实例（或 SA 自己）汇总成一份报告，只落一条带 `--decision` 的账；其他实例落账时在 `--note` 里写明自己负责哪一份。
- 机器一忙就容易误判的工作（如对负载敏感的用例组）串行执行。
- 同一实例内开多路进程（如 QA 执行器分路跑用例）同样适用上述隔离条件；本工程的隔离参数见工程配置「命令」。
- 只写文档的实例留在主工作树；写代码的线各在自己的工作树里。同一工作树内的各实例（以及 SA 自己）共用一个 git 暂存区：**提交一律带路径**，只列本实例负责的路径，按 `AGENTS.md`「多角色同 worktree 下的提交纪律」执行。路径不重叠是前提，带路径提交保证一方先暂存的改动不会被另一方的提交带走。

### 取证口径

- 评审以指定的已提交版本为准；HEAD 不同或工作树有未提交改动时，可直接读取指定提交，不将其他改动作为评审依据。
- 修改和测试须确认实际使用的工作树及版本；读取工作树取证时，确认所读内容与依据版本一致。
- 无法定位版本或存在影响本任务的输入冲突时，停止受影响部分并报告 SA，不猜测版本继续。

### 交付

回报结果、关键证据、未完成部分和下一步；状态变更按 `skills/team-ledger/SKILL.md` 落账，需要其他角色接手时写明交给 SA。

## 四、争议归口与升级

- **争议归口**：需求 / 范围 / 体验 → **PM 终裁**；技术 / 架构 / 执行 → **SA 终裁**；质量 → QA 报告里标 `阻断`，**由产品负责人在一句话确认时裁定**。
- **PM 与 SA 之间的分歧无内部仲裁人**（SA 已是技术当事人）→ 直接升级产品负责人，不得由任一方自裁。
- **升级产品负责人（仅高风险，经 SA）**：需求方向重大变更 / 架构级返工 / 高影响面风险 / 破坏性不可逆操作。
- **契约有洞**（无规则或规则打架）→ 落账写明 `契约缺口: <一句话>` ＋ 提请 SA。**不擅自补规则往下跑。**
- **BUG 分级**：简单 BUG → SE 修（快速链路）；复杂 BUG（含根因在需求 / 设计层）→ 增量链路，PM 先为它立需求说明（§二.1 入口 ③）。

## 五、评审与合入

**评审只建议，合入一句话。**

- **评审是建议，不是门。** 判定仍记 `APPROVED` / `CR`，但 `CR` **不阻断下一步**；被评方读完自决改不改，在账本 note 写明「采纳 / 不采纳 ＋ 一句理由」。
- **轮次封顶 1。** 每份产物最多一轮评审；评审方给 `CR`，被评方修完**不再回评**。
- **不写评审记录文件。** 评审结论只落账本（`--decision` ＋ `--note`），不再落 `docs/reviews/`。角色产物（需求文档、设计、spec+plan、方案+用例、测试报告）照常落 `docs/`。
- **SA 不复跑。** 采信各角色自报的测试数字；SA 只核形状 —— 产物已提交、`commit:path` 可读。
- **证据指针保留。** 被评产物**必须先提交**并以 `commit:path` 指认，评审按 §三取证口径以指定版本为准。
- **发现分级保留** `阻断`/`高风险`/`一般`/`建议`，QA 报告里写明；**`阻断` 不自动拦合入**，由产品负责人在一句话确认时裁定。
- **需求覆盖度对账保留**（全链路、增量链路）：spec+plan 里每条 US / NFR / AC 映射到某 task 或显式标 `deferred`，差集在 PM 需求符合性结论里点名，禁止静默丢弃。
- **原型不得被引为任何 AC 的通过证据** —— 它是形态的事实源，不是行为证据。原型上的改动按需求改动处理：先改需求文档，再改原型。
- **合入决定权 ＝ 产品负责人一句话。** 线合入集成分支是 SA 的集成动作；集成分支进 `main` 要等自上次进 `main` 以来合入的各项都已验收通过（`并行线.md`「七」）。SA 按版本启动时确定的分支策略及产品负责人本次授权合入、推送、落账，合入 `main` 时使用 `--no-ff`；迭代交付和版本最终合入分别处理，不能因一次迭代验收擅自结束版本。**不再有 PM / SA 签字。**
- **DoD** ＝ 产物已提交 ＋ 账本落终态。

## 附：状态账本

每次状态变更即落账。账本只有三条命令（`append` / `stale` / `owner`），用法见 `skills/team-ledger/SKILL.md`：

```
team-ledger.py append --role <me> --item <工作项> [--part <子产物>] --status <进行中|待评审|评审中|阻塞|完成|交接> \
  [--to <接续方>] [--blocker-role <被卡方>] \
  [--phase ...] [--round N] [--decision APPROVED|CR] [--note '一句话']
```

**非终态必须指定接续方**，SA 据此读出待派的棒。`交接` / `待评审` 用 `--to <角色>`；`阻塞` 用 `--blocker-role <角色>`。不指定即拒绝落账。

- **接续方是产品负责人**（等裁定 / 等排期）→ 写 `--blocker-role owner`：进**待裁决清单**（`team-ledger.py owner` 查），由人处理。

**粒度：一个 `--item` ＝ 一条独立的评审线。** 判据：**若两件事会各自独立地被评审 / 被合入，它们就是两个工作项**，不得共用一个 item 名。快速链路一个工作项通常只有 `<名>-需求` / `-开发` / `-测试` / `-合入` 四条。当前态逐项核用 `team-ledger.py stale --hours 0`。**存量不追溯，新工作项适用。**

**同一工作项内并行的子产物，落账必须带 `--part <子产物名>`**（如主线 SE 开发时，PM 澄清其中一份子产物）。子产物只管自己那一行；整项只在主线落 `完成` 时收口，`交接` 不收口整项。不带 `--part` 时，子线的落账会被当成主线的状态。

`append` 对同事异名（大小写 / 空格 / 连字符 / 全角差异）**硬拒**，确属另起才用 `--force-new-item` ＋ `--note` 写明理由。
