# 双端协作与交接

本工程支持在 Claude Code 与 Codex 之间接力。两端使用同一角色职责和产品开发契约，SA 由当前主会话承担；PM、UI、SE、QA 由当前宿主的 subagent 承担。工程基建仍由 SA 直接完成。运行纪律见契约 §三「两端运行纪律」，本文写配置位置、派活适配与换端步骤。

## 配置位置

| 内容 | 事实源 | Claude Code 入口 | Codex 入口 |
|---|---|---|---|
| 项目规范 | `AGENTS.md` ＋ `docs/rules/工程配置.md` | `CLAUDE.md` 引用 | 自动读取 `AGENTS.md` |
| 角色职责 | `docs/rules/roles/{pm,ui,se,qa}.md` | `.claude/agents/*.md` | `.codex/agents/*.toml`，并在 `.codex/config.toml` 注册 |
| 项目 skills | `skills/` | `.claude/skills` 软链 | `.codex/skills` 软链 |
| 协作进度 | 主工作树 `.team-ledger/ledger.jsonl` | `skills/team-ledger/team-ledger.py` | 同一工具、同一本账 |

- 角色正文只在 `docs/rules/roles/` 修改，两端入口只保留简短描述和「开始任务前完整读取并遵循」的指令，不复制职责正文。普通文件引用不会由宿主自动展开，subagent 必须主动读取。
- 元数据 `tools` 是 Claude 的工具列表，不直接映射为 Codex 工具名。Codex 的权限、可用工具和模型继承当前父会话；角色职责边界不等于操作系统沙箱。
- 不固定任一厂商模型，不改用户级配置，不代管两个工具的登录和额度。
- 新增或更名角色时，同步更新两端入口及 `.codex/config.toml` 注册，并核对引用路径存在。更改配置后在项目目录重新打开主会话；已有子会话不视为已更新。
- 已有 worktree 不会自动得到新增的基建文件。要从旧 worktree 启动新主会话，先按分支策略带入基建提交；暂不合并时，由主工作树 SA 在任务中给出共享角色文档的实际绝对路径，要求 subagent 先读取，并明确产品工作树和候选版本。

## 派活适配

| 需求 | Claude Code | Codex |
|---|---|---|
| 按角色派活 | 当前宿主的 Agent / Task 工具，选择 pm / ui / se / qa | 宿主支持自定义角色时，选择 pm / ui / se / qa |
| 只暴露通用 spawn 工具 | 传入共享角色文档引用、读取指令和任务 | 同左；不得假设自定义 TOML 已由通用工具自动注入 |
| 等待交付 | 同步结果或当前宿主的任务等待机制 | 用当前宿主提供的等待 / 消息工具，拿到实际结论 |
| 查看活动任务 | 当前 Claude 会话的任务列表 | 当前 Codex 会话的 agent 列表 |
| 账本巡检 | 按 `team-ledger` skill「SA 值守的每回合三步」：每次派活前、收回结论后、恢复会话时重读账本 | 同左 |

- 用通用工具派活时，SA 附上 `docs/rules/roles/<角色>.md` 的引用和「开始任务前完整读取并遵循」的明确指令，再按 `docs/rules/派活与交付.md`「一、派活单」追加各字段（目标与预期产物、工作依据、工作项等）。subagent 读取不到应报告派活方并停止，不凭记忆补写职责。工作目录不在项目根或使用旧工作树时，派活方提供共享文件的实际绝对路径。角色不能再次派出其他角色。
- 工具名随宿主提供的 schema 使用，不在 Codex 中调用 Claude 专属工具，也不虚构不存在的参数。消息已发送不等于任务已完成；同步或异步都要在本次调度中收回交付、落账，再接下一棒。

**PM 直接需求讨论**：Claude 可用 `claude --agent pm`；Codex 在项目中新开会话，输入「请先完整读取 `docs/rules/roles/pm.md`，按 PM 角色与我讨论需求，遵守其中必读文件与职责边界」。该会话此时是 PM，不同时充当 SA；完成需求后交接 SA 值守会话。

## 额度耗尽或切换工具

接力依靠落盘事实恢复任务，不能迁移原工具的内存、活动子会话或权限确认。

1. 旧 SA 停止派新任务，收回或中断自己派出的活动任务；中断的测试标明未完成。不终止用户或其他会话的进程。额度已耗尽时，由新 SA 先核原进程和工作树状态，确认没有并发写入后再接续。
2. 核对 `git status --short`、`git worktree list` 和原 item 最新账本记录；`git worktree list` 与账本里登记的并行线逐条对上，不认账本以外的工作树（例如工具自建的）。完成的产物按原流程提交；未完成的改动保留在原工作树，记录路径、分支、HEAD、未提交文件及归属，不强制提交半成品，不清理工作树。
3. 在主工作树 `.team-ledger/handoff.md` 写一份当前交接说明（不入库，不含真实密钥）。它是导航，状态事实仍以账本和 git 为准。至少包括：

```text
更新时间、旧宿主、接续宿主、当前产品版本
原 ledger item、角色、阶段、链路与用户已批准的约束
工作树、分支、HEAD、产物 commit:path、未提交改动及归属
已完成验证的命令/结果；中断或未运行的验证
活动任务/进程是否结束；待处理发现；下一棒及其输入
用户尚未确认的事项（如合入、生产部署），不可冒记授权
```

4. 在新工具中打开**同一个项目目录**，重新加载项目配置（Codex 第一次在本工程使用时，先执行 `/hooks` 信任本工程的钩子）；先读 `AGENTS.md`、`docs/rules/工程配置.md`、本文、交接说明（如有），再读账本：`python3 skills/team-ledger/team-ledger.py stale --hours 0` 与 `owner`。
5. 逐项核交接内容和真实工作树。旧「进行中」不代表仍有活动 agent；旧宿主任务 ID 不在新宿主续用。用**原 item、原产物版本**重新派出剩余步骤；已完成的评审与 QA 线不重开；未合入的并行线按原分支、原工作树续派，不新开线。用户已明确的范围、跳过项与授权继续有效，不能从旧部署记录推定新功能已授权部署。

可直接粘贴到新主会话：

> 请作为本项目 SA 接班。先读取 AGENTS.md、docs/rules/工程配置.md、docs/rules/双端协作与交接.md 和主工作树 .team-ledger/handoff.md（如有），核对 git 工作树与状态账本，汇报实际接力点，然后按原 item 继续未完成工作。产品任务按契约派 PM/UI/SE/QA，通用 spawn 工具须引用对应的 docs/rules/roles 文档并要求 subagent 先完整读取。不要重开已完成的步骤，不要与旧会话并发修改。

活跃账本不入 git，**换电脑或重新克隆不会带走活跃流**。跨机器接力须另外安全传递活跃账本、交接说明、未提交改动及必要证据；不要用提交真实凭据的方式搬环境。
